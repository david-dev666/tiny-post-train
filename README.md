# tiny-post-train

Qwen3-4B 的后训练全流程开源项目：SFT -> DPO -> GRPO -> 评测 -> 部署。

## 目标

在单卡 24G 显存上，用一套可复现的脚本跑通小模型后训练的完整链路，并给出真实评测对比，而不是只贴一个 loss 曲线。

## 流程

| 阶段 | 方法 | 脚本 | 状态 |
| --- | --- | --- | --- |
| 0 | 环境搭建 | scripts/setup_env.sh | 可用 |
| 1 | SFT 监督微调 | scripts/train_sft.py | 已跑通（4B / LoRA r=32 / 1 epoch，约 1.1 GPU 小时） |
| 2 | DPO 偏好对齐 | scripts/train_dpo.py | 未实现 |
| 3 | GRPO 可验证奖励强化 | scripts/train_grpo.py | 未实现 |
| 4 | 评测 | scripts/eval.py | 可用（5 套评测 + 置信区间 + 可切换推理引擎） |
| 5 | 推理部署 | scripts/serve_vllm.sh | 未实现（评测侧的 vLLM 已跑通，见 scripts/engines.py） |
| 辅助 | 训练看板 | dashboard/server.py | 可用 |
| 辅助 | 多模型评测 pipeline | scripts/eval_pipeline.py | 可用（跑完自动出 HTML 报告） |
| 辅助 | 评测报告 | scripts/make_report.py | 可用（自包含 HTML，零外部依赖） |
| 辅助 | 离线重判 | scripts/rescore.py | 可用（改判分口径不必重跑模型） |
| 辅助 | 判分回归测试 | tests/test_scoring.py | 可用（34 条，不依赖 GPU） |

## 实验设计

- 基座：Qwen/Qwen3-4B-Base
- 对照基线：Qwen/Qwen3-4B-Instruct-2507，官方对齐版，用于说明自训流程与官方流程的差距
- 冒烟模型：Qwen/Qwen3-0.6B-Base，用于验证脚本管道，几十分钟就能跑完一轮

从 Base 起步而不是从 Instruct 起步，是为了让 SFT 这一步是真实可控的，整条链路才是完整的后训练。

## 训练看板

训练脚本会把指标追加写到 `outputs/<run>/metrics.jsonl`，看板读这个文件实时画曲线。

```bash
bash scripts/start_dashboard.sh          # 起服务
bash scripts/start_dashboard.sh stop     # 停
bash scripts/start_dashboard.sh token    # 只看口令
```

看板默认跑在 **6006**，并自动生成访问口令（存在 `logs/dashboard.token`，已被 gitignore）。每次启动复用同一个口令，所以手机书签长期有效。

**手机 / 任意设备**：把 AutoDL 实例卡片「自定义服务」里 **6006 那条**域名接上口令打开：

```
https://<你的实例域名>/?token=<口令>
```

**Mac 走 SSH 隧道**（不经过公网，等价可用）：

```bash
ssh -N -L 6006:localhost:6006 autodl
# http://localhost:6006/?token=<口令>
```

看板显示：

| 类别 | 内容 |
| --- | --- |
| 曲线 | train loss、eval loss、perplexity、learning rate、MMLU 子集准确率 |
| 进度 | 当前步数 / 总步数、预计剩余时间 |
| 硬件 | GPU 利用率、显存、温度、功耗 |
| 健康 | 训练进程是否存活 |
| 配置 | 基座模型、数据路径、超参、验证集大小 |
| 数据 | 训练数据抽样 3 条（真实喂进去的样本） |
| 推理 | 固定问题的生成结果（最新 + 上一次对比），附复读率 / 生成长度 |

### 指标说明（别误读）

| 指标 | 含义 | 别当它是 |
| --- | --- | --- |
| `train loss` | 对训练集的拟合程度 | 回答质量 |
| `eval loss` | 对验证集的拟合程度 | 回答质量 |
| `perplexity` | `exp(eval_loss)`，同样只反映拟合度 | 回答质量。**过拟合时它照样降** |
| `复读率` | 生成里重复 2-gram 的占比 | 质量分。只用来发现**退化**（复读率飙升 = 崩了） |
| `词面多样` | 不同 token 的占比 | 质量分。太低说明输出单调 |
| `MMLU 子集准确率` | 固定题目上的多选题正确率 | 综合能力。**用指令数据做 SFT 通常不会提升它，甚至下降**（灾难性遗忘），这是常见现象不是 bug |

**故意没有做的**：不自动算 ROUGE / BLEU，也不给生成结果打质量分。采样的三个问题都是开放式的，没有唯一正确答案，硬套参考答案算出来的数字看着精确、实则误导。真正的效果要看生成结果本身，以及后续 `eval.py` 跑出来的基准评测。

### 基准评测（训练中）

MMLU 全量 14042 题，4B 上跑一遍要一两个小时，比训练还慢，所以用**固定子集**：

```bash
python scripts/bench_subset.py     # 生成 evals/mmlu-subset.jsonl（57 学科 × 8 题 = 456 题）
```

```bash
--bench-every 100                  # 每 100 步在子集上评一次
```

几个要点：

- **子集必须固定**（`--seed` + 只抽一次落盘）。每次重抽的话，题目难度变化会被误读成模型退步。
- **`evals/mmlu-subset.jsonl` 要提交进版本库**，SFT / DPO / GRPO 三阶段的分数才可比。
- 判分只比 A/B/C/D 四个 token 的 logits，不做生成，一次前向就够——所以它测的是「模型更倾向输出哪个字母」，**不等于模型会答题**。
- 国内直连 `huggingface.co` 会超时，脚本默认走 `hf-mirror.com`，可用 `--hf-endpoint` 换。
- 也可以 `--source /path/to/local.jsonl` 完全绕开网络。

### 实时评测指标怎么产生

```bash
--eval-ratio 0.02     # 从训练集切 2% 当验证集（默认）
--eval-steps 50       # 每 50 步评一次
--probe-every 50      # 每 50 步用固定问题采样一次生成，0 表示关闭
```

验证集切分用 `--seed` 固定，**换 seed 曲线就不可比**。

### 关于安全

- 服务**只绑 `127.0.0.1`**。AutoDL 的公网映射转发的是容器内 localhost，所以手机照样能访问，但容器内不会多开一层监听面。
- **口令是必须的**。6006 公网可达，没口令等于把训练数据挂在网上。口令在 URL 里传一次，之后前端存 localStorage 并改用 `X-Token` 请求头。
- 只在隧道场景下想省掉口令：`ENABLE_AUTH=0 bash scripts/start_dashboard.sh`。
- 6008 是另一条映射端口，留给 TensorBoard 用，别和看板抢。

## 结果

**全量口径**（不是抽样）：MMLU 14042 题（两种提问口径各跑一遍）+ 指令遵循 200 条
+ GSM8K 官方 test 1319 题 + HumanEval 164 题。括号内是 Wilson 95% 置信区间半宽（pp）。

**推理引擎 vLLM，三个模型跑完全部只用 21 分钟**（HF 逐条生成要 2 小时 56 分，16.7×）。
换引擎让「跑全量」从一件要计划一晚上的事变成随手就能做的事 —— 上面那批数字是**全量**，
不是抽样，这一点比什么都重要。
**下表全部由同一个引擎产出（vLLM），只有一把尺子**；换引擎要整批重跑。

| 模型 | MMLU（chat） | MMLU（纯文本） | 指令遵循 | GSM8K（数学） | HumanEval（代码） |
| --- | --- | --- | --- | --- | --- |
| `base-4b`　Qwen3-4B-Base（基线） | 0.0% ±0.03 | 69.5% ±0.76 | 36.0% ±6.59 | 67.8% ±2.52 | 65.8% ±7.18 |
| `sft-4b-v2`　自训 LoRA SFT | 68.3% ±0.77 | **70.2%** ±0.76 | 61.0% ±6.70 | 83.6% ±1.99 | 72.6% ±6.77 |
| `instruct-2507`　官方对齐版（对照） | 67.7% ±0.77 | 64.2% ±0.79 | **97.5%** ±2.32 | **91.3%** ±1.52 | **84.8%** ±5.50 |

**读这张表之前必须知道的三件事：**

1. **MMLU 有两列，别只看 chat 那一列。** chat 口径把「答案：」放在 user 回合内，
   带对话模板的模型会正常作答；**基座却把整份提示当成一份已写完的文档，接着去开下一题** ——
   14042 题里有 14035 题一个选项字母都没生成。所以 base 的 `0.0%` 不是「不会做题」，
   而是**这个口径对它无效**，它的真实水平看「纯文本」那一列
   （换掉 chat 包装后 0% → 69.5%，**且 0-shot 就够**：0/1/2/3/5-shot 实测完全一样）。
   报告里这种格子会自动判定「口径无效」并说明成因。

2. **同口径下三者 MMLU 在 6pp 以内**（69.5 / 70.2 / 64.2）。
   这符合预期：**用通用指令数据做 SFT 不会提升知识型 MCQ**，它改的是「按什么格式回答」，
   不是「知道多少」。所以「base 0% → SFT 68.3%」这种跨口径的写法是错的，不要用。

3. **GSM8K 的排序是 instruct > SFT > base（91.3 / 83.6 / 67.8）。**
   早期版本这里写的是「SFT 83.0%，高于官方 instruct 的 51.7%」——**那个结论是错的**，
   成因有两层：GSM8K 只跑了前 400 题，且生成上限被设成 **256 token**，
   而 instruct-2507 写的是啰嗦的 markdown 解题，**答案还没写出来就被截断了**。
   改成 1024 token + 全量 1319 题之后，它回到 91.3%。
   **「啰嗦」被算成了「不会」** —— 这是本轮修正掉的第二个假结论。
   已确认用的是 GSM8K **官方 test split**，不存在测试集泄漏。

**三条真实结论：**

- **SFT 的价值集中在「格式与指令」，不在知识。** 指令遵循 36.0% → **61.0%**（+25pp），
  而 MMLU 想拿到分本身就依赖先学会「吐一个字母」。这两个方向是同一件事。
- **SFT 在数学上真的变强了：GSM8K 67.8% → 83.6%（+15.8pp）**，且 HumanEval 也涨
  （65.8% → 72.6%）。
- **和官方 instruct 的差距主要在代码、指令遵循和数学**（72.6% vs 84.8%、61.0% vs 97.5%、
  83.6% vs 91.3%）。`instruct-2507` 的数值约束 / 格式约束 / 代码约束三类全是 25/25 满分 ——
  这是它真正的强项，也正是自训 SFT 下一阶段（DPO）该补的地方。

交互式报告见 `evals/results/report.html`（自包含，零外部依赖）；
**评测怎么跑、怎么读、判分踩过哪些坑，见 [`docs/01-评测.md`](docs/01-评测.md)**。

> 更早那版 **HF 引擎**的结果（只跑了 400 题）存在 `evals/archive/hf-engine/`，**不参与任何对比**。
> 换引擎会让绝对分数小幅变动（bf16 下是两条数值路径，实测同一批 50 题逐题预测翻转 13 题），
> 拿新旧引擎的数字并排看没有意义 —— 所以没在仓库里当基准留着。
> 报告检测到混引擎会直接报警。

### 这张表可信吗

报告里还有一张「可信度诊断」表，四个数：**被截断 / 乱码尾 / 兜底抽取 / 口径无效**。
它们不参与判分，但决定上面这张表能不能用 —— 比如 `--gsm8k-max-new-tokens 256` 会把
啰嗦模型的答案截断在最终给数之前（就是上面第 3 点修掉的那个），
**风格差异会被算成能力差异**，所以这类信号必须摆在明面上。

## 硬件与成本

**单卡 RTX 4090 24G**（实测 24564 MiB，driver 580.76.05；宿主 128 核 / 1TB 内存，
容器挂 50G 数据盘）。两套 Python 环境互不干扰：

| 环境 | 用途 | 关键版本 |
| --- | --- | --- |
| `tpt` | 训练 + HF 引擎推理 | torch 2.12.1+cu130 / transformers 5.5.0 / unsloth |
| `vllm` | 评测（vLLM 引擎） | torch 2.13.0+cu130 / transformers 5.18.0 / vllm 0.30.0 |

> 装不到一起：vLLM 要 torch 2.13，unsloth 锁在 2.12.1。硬合会把训练搞坏，所以分成两套。

### GPU 小时

| 阶段 | 实测 | 说明 |
| --- | --- | --- |
| SFT 4B · **1 epoch（v2，在用）** | **1.1 h** | 2991 步；LoRA r=32 / 等效 batch 16（micro 4 × accum 4）/ max-seq-len 2048；alpaca-gpt4-zh 约 4.8 万条 |
| SFT 4B · 2 epoch（v1，已弃用） | 2.4 h | 5982 步。eval loss 在 ~step 2900 就走平了，第二个 epoch 是白跑 —— v2 才改成 1 epoch |
| 训练冒烟（0.6B） | 0.04 h | 只验链路 |
| **vLLM 引擎 · 三模型全量评测** | **0.35 h** | 21 分钟 |
| HF 引擎 · 三模型全量评测 | 2.9 h | 176 分钟，仅历史 |
| 失败重跑与探针 | ~1.5 h（估） | `splitlines` 崩溃、GSM8K token 上限、引擎 A/B 复现性 —— 见 `docs/01-评测.md` 的「判分 bug 史」 |
| 环境搭建 / 下权重 | 走**无卡模式**（0.1 元/时） | 不占 GPU 小时 |

**合计约 9~10 GPU 小时。** 除最后一行外都是日志里量出来的；单价按 **¥2/小时** 量级
（项目记录；2026 年外部比价 4090 最低约 ¥2.15/小时）：**总花费约 20 元**。
精确账单以平台后台为准 —— 这张表的用处是看**钱花在哪**，不是对账。

### 这些数字说明了什么

**GPU 时间几乎全花在「试错」上，而不是训练。** 训练只占 1.1 小时，
而排查问题（判分 bug、token 上限、引擎切换）花了 1.5 小时以上 —— 单看训练，这笔账像是浪费；
但那些排查改掉的是**结论本身**（两个假结论被推翻，见上面「结果」一节），不是几行代码。

**vLLM 把「跑一次全量评测」从 2.9 小时压到 0.35 小时**，只占一次训练的 1/3。
它省的不是钱（都是几分钱），是**决策速度**：以前出一个数要计划一晚上，现在随手就跑 ——
于是「为了省时间抽样」这个动机直接消失了。上面那个 GSM8K 假结论正是抽样 + 截断造成的。
