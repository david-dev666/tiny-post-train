# tiny-post-train

Qwen3-4B 的后训练全流程开源项目，覆盖 SFT、DPO、GRPO、评测与部署。

在线评测报告（GitHub Pages）：<https://david-dev666.github.io/tiny-post-train/>

## 项目概要

目标是在单卡 24G 显存上，以一套可复现的脚本完成小模型后训练的完整链路，并给出基于全量测试集的真实评测对比，而不是仅提供训练损失曲线。

已完成的工作与关键结果如下：

| 项 | 结果 |
| --- | --- |
| 评测口径 | 全量，非抽样。MMLU 14042 题、指令遵循 200 题、GSM8K 官方 test 1319 题、HumanEval 164 题 |
| 对比模型 | 四个。base / 自训 SFT / ＋开源 DPO / 官方 instruct，同一判分栈、同一推理引擎 |
| 推理引擎 | vLLM。全套全量评测约 21 分钟（HF 逐条生成需 2 小时 56 分） |
| DPO 效果 | HumanEval 追至与官方 instruct 相差 1 题（139/164 对 140/164） |
| 失败记录 | 收尾乱码尾训练侧 13 次证否、GRPO 一轮负结果；方法、根因与处置均保留在仓库中 |

### 收尾乱码尾：自训 SFT 引入的缺陷，训练侧 13 次尝试全部未成功

v2 的输出在回合结束前会额外生成一个乱码 token（如希伯来语词 `לחלוט`、残缺字节 `\ufffd\ufffd取`）。在模型自行决定收尾的样本中，该现象出现率为 92%~94%；而 base 为 0~2.5%，官方 instruct 为 **0.0%**。因此该缺陷由自训 SFT 引入。

收尾位置的靶心已完成量化：`<|im_end|>` 排名第 4，与排名第一的乱码 token 仅相差 **0.13 nats**。可操作窗口极小，且任何序列级训练信号都无法作用于该位置。三类机制、共 13 次尝试均未成功：

| 机制 | 轮数 | 代表做法 | 结果 |
| --- | --- | --- | --- |
| SFT 侧 | 6 | 末位 loss / 收尾加权 ×20 / eos 对齐 / 改用模型自生成数据 / 从 Base 重训（v3） | 全部未成功。v3 表面上将乱码尾降至 0，实则变为**「不会收尾」**（用满 token 上限 200/200；指令遵循 61.5%→45.0%、GSM8K 83.2%→72.8%） |
| DPO | 5 | 整条序列 / 末位 1-token / eos 对齐 / 第 5 轮 1 epoch + 小 lr | 曲线均正常（`acc` 达到 1.0），靶心 logit 仅移动 **0.06 nats**；`<|endoftext|>` 反而被压低 5.16 nats |
| RFT | 2 | 拒绝采样（仅在模型「答对且输出干净」的样本上继续训练） | 第一轮因 3 epoch / lr 1e-4 / 纯 GSM8K 导致停止能力坍塌；修正后不再坍塌，乱码尾仅变化 2~3pp |

唯一实测有效的方案位于解码侧：将 `<|im_end|>` 的 logit 提高 +2.0，指令遵循由 61.5% 提升至 **80.5%**，乱码尾降至 0。该方法属于解码技巧，不计入后训练成果，归入「阶段 5 推理部署」。

一项应纳入验收标准的判据：总 `junk_tail` 会因「模型无法停止」而被拉低，v3 与 RFT 第一轮均借此制造了指标改善的假象。因此，任何 adapter 必须同时报告三个数值：**用满 token 上限的样本数**、**自然收尾样本中的乱码尾率**、**主指标**。该问题在项目中重复出现三次（v3、RFT 第一轮）。

### GRPO：第 14 次证否，「方法是否有效」尚无法判定

针对上文结论「指令遵循是下一阶段应补齐的部分」（61.0% 对 98.5%），使用 **GRPO + IF-RLVR**（AI2，arXiv 2507.02833）进行了一轮尝试。主指标提升 **0.0pp**（120/200 → 120/200），无正式结果。两条可确定的归因如下：

1. **奖励形式无法作用于瓶颈。** 主指标 50 分的缺口集中在「数值约束 0/25、长度约束 2/25」两类，其失败方式为答对后收尾多生成一个乱码 token（如 `72` → `72 לחלוט`），从而违反「纯数字」约束。GRPO 的奖励是整条序列的函数，无法作用于单个 token，属结构性限制，在实验开始前即已确定。
2. **更新幅度过小。** `lr=1e-6` 取自论文的全参设置，而本实验使用 LoRA（常见 lr 应高 10~100 倍）；`kl` 均值 0.0009，策略几乎未偏离起点。

旁证：`junk_tail` 由 178 升至 **184**（未降反升）；其他能力（MMLU / GSM8K / HumanEval）均处于重跑抖动范围内，未出现退化。

更关键的是，本轮「方法本身是否有效」无法判定：训练使用英文约束（IFEval 25 + IFTrain 29），评测使用项目自建的中文模板题，两者不同源；而论文的标准度量 **IFBench**（58 个全新约束、299 条 held-out）尚未运行。论文指出模型会过拟合到 IFEval 的 25 个模板，而训练数据恰好包含这 25 个模板——训练集 reward 升至 0.319 有可能来自模板记忆，仅 IFBench 可对此作判定。完整归因与边界见 [docs/02-GRPO尝试.md](docs/02-GRPO尝试.md)。

## 实验设计

- 基座：Qwen/Qwen3-4B-Base
- 对照基线：Qwen/Qwen3-4B-Instruct-2507，官方对齐版，用于说明自训流程与官方流程的差距
- 冒烟模型：Qwen/Qwen3-0.6B-Base，用于验证脚本管道，数十分钟即可完成一轮

从 Base 而非 Instruct 起步，是为了使 SFT 阶段真实可控，从而构成完整的后训练链路。

## 训练看板

训练脚本将指标追加写入 `outputs/<run>/metrics.jsonl`，看板读取该文件实时绘制曲线。

```bash
bash scripts/start_dashboard.sh          # 启动
bash scripts/start_dashboard.sh stop     # 停止
bash scripts/start_dashboard.sh token    # 查看口令
```

看板默认监听 **6006** 端口，并自动生成访问口令（保存在 `logs/dashboard.token`，已被 gitignore）。每次启动复用同一口令，移动端书签可长期使用。

**移动端或任意设备**：打开 AutoDL 实例卡片「自定义服务」中 **6006** 对应的域名，并附上口令：

```
https://<实例域名>/?token=<口令>
```

**Mac 通过 SSH 隧道**（不经过公网，功能等价）：

```bash
ssh -N -L 6006:localhost:6006 autodl
# http://localhost:6006/?token=<口令>
```

看板显示内容：

| 类别 | 内容 |
| --- | --- |
| 曲线 | train loss、eval loss、perplexity、learning rate、MMLU 子集准确率 |
| 进度 | 当前步数 / 总步数、预计剩余时间 |
| 硬件 | GPU 利用率、显存、温度、功耗 |
| 健康 | 训练进程是否存活 |
| 配置 | 基座模型、数据路径、超参、验证集大小 |
| 数据 | 训练数据抽样 3 条（实际输入样本） |
| 推理 | 固定问题的生成结果（最新与上一次对比），附复读率、生成长度 |

### 指标说明

| 指标 | 含义 | 不代表 |
| --- | --- | --- |
| `train loss` | 对训练集的拟合程度 | 回答质量 |
| `eval loss` | 对验证集的拟合程度 | 回答质量 |
| `perplexity` | `exp(eval_loss)`，同样只反映拟合度 | 回答质量。过拟合时仍会下降 |
| `复读率` | 生成中重复 2-gram 的占比 | 质量分。仅用于发现退化（复读率显著上升即说明输出崩溃） |
| `词面多样` | 不同 token 的占比 | 质量分。过低说明输出单调 |
| `MMLU 子集准确率` | 固定题目上的多选题正确率 | 综合能力。使用指令数据做 SFT 通常不会提升该指标，甚至下降（灾难性遗忘），属常见现象，并非缺陷 |

**未实现的部分**：不自动计算 ROUGE / BLEU，也不对生成结果打分。采样问题均为开放式，无唯一正确答案，套用参考答案计算出的指标表面精确、实际具有误导性。实际效果应以生成结果本身以及 `eval.py` 的基准评测为准。

### 基准评测（训练中）

MMLU 全量 14042 题在 4B 模型上单次评测需一到两小时，慢于训练本身，因此使用**固定子集**：

```bash
python scripts/bench_subset.py     # 生成 evals/mmlu-subset.jsonl（57 学科 × 8 题 = 456 题）
```

```bash
--bench-every 100                  # 每 100 步在子集上评测一次
```

要点：

- **子集必须固定**（`--seed` 且仅抽样一次并落盘）。若每次重新抽样，题目难度的变化会被误判为模型退步。
- **`evals/mmlu-subset.jsonl` 应提交进版本库**，以保证 SFT / DPO / GRPO 三阶段的分数可比。
- 判分仅比较 A/B/C/D 四个 token 的 logits，不做生成，一次前向即可完成。因此该指标衡量的是「模型更倾向于输出哪个字母」，**不代表模型能够正确答题**。
- 国内直连 `huggingface.co` 会超时，脚本默认走 `hf-mirror.com`，可用 `--hf-endpoint` 更换。
- 也可通过 `--source /path/to/local.jsonl` 完全绕过网络。

### 实时评测指标的生成

```bash
--eval-ratio 0.02     # 从训练集切分 2% 作为验证集（默认）
--eval-steps 50       # 每 50 步评测一次
--probe-every 50      # 每 50 步用固定问题采样一次，0 表示关闭
```

验证集切分由 `--seed` 固定；更换 seed 后曲线不可比。

### 安全性

- 服务仅绑定 `127.0.0.1`。AutoDL 的公网映射转发的是容器内 localhost，因此移动端仍可访问，同时容器内不额外暴露监听端口。
- **口令为必需项**。6006 端口可经公网访问，无口令等同于公开训练数据。口令首次通过 URL 传递，之后前端保存至 localStorage 并改用 `X-Token` 请求头。
- 仅在 SSH 隧道场景下可省略口令：`ENABLE_AUTH=0 bash scripts/start_dashboard.sh`。
- 6008 为另一条映射端口，预留给 TensorBoard。

## 结果

以下结果均为**全量口径**，非抽样：MMLU 14042 题（两种提问口径各跑一遍）、指令遵循 200 条、GSM8K 官方 test 1319 题、HumanEval 164 题。括号内为 Wilson 95% 置信区间半宽（单位：百分点）。

推理引擎为 vLLM，三个模型跑完全部仅需 **21 分钟**（HF 逐条生成需 2 小时 56 分，约 16.7 倍）。更换引擎使全量评测从需要提前规划变为可随时执行，因此上述数字为全量而非抽样。下表全部由同一引擎（vLLM）产出，只有一把尺子；更换引擎需整批重跑。

### 评测公平性：两条硬规则

**规则一：评测任何模型时，不允许使用任何推理优化或人为技巧干预。**

禁止：抬高特定 token（如 `<|im_end|>`）的 logits、`logit_bias`、`repetition_penalty` / `presence_penalty` / `frequency_penalty`、`bad_words`、`min_tokens` 等长度约束，以及任何 `logits_processor` 回调或被修改的 chat template。

允许：`temperature=0` 贪心解码、`top_p=1.0`、`max_tokens`、`stop_token_ids`、`skip_special_tokens`。（`max_tokens` 是预算而非技巧，但必须一视同仁并公开，见规则二。）

原因：任何解码干预都会混淆「模型是否具备该能力」与「是否允许其表现」，跨模型对比随即失去意义。本项目曾因此产生误导——将 `<|im_end|>` 的 logit 提高 +2.0 后，指令遵循可由 61.0% 达到 **80.5%**、乱码尾降至 **0**，但该结果属于解码技巧，模型本身未发生变化。因此那批实验（`sft-boost` / `probe-boost`）已从结果目录移入 `evals/archive/`，**不参与任何对比**；相关补丁代码已删除，`scripts/` 中不含任何 `logits_processor` / `logit_bias` / penalty 参数。

**规则二：所有参与对比的模型，必须在同一判分栈上重跑，并公开截断数。**

判分代码一经修改，历史数字即不可并列（本项目实测：同一模型更换判分栈后 GSM8K 变动 1.2pp，已不小于重跑抖动 0.5pp）。同时必须报告「用满 token 上限的样本数」，否则「未写完」会被误判为「不会」（GSM8K 256-token 的假结论即由此产生；HumanEval 上 `sft-4b-v2` 有 57/164 条被截断，直接使代码分数虚低 11pp）。

| 模型 | MMLU（chat） | MMLU（纯文本） | 指令遵循 | 指令遵循（去尾） | GSM8K（数学） | HumanEval（代码） |
| --- | --- | --- | --- | --- | --- | --- |
| `base-4b`　Qwen3-4B-Base（基线） | 0.0% ±0.03 | 69.5% ±0.76 | 39.5% ±6.72 | 39.5% | 68.0% ±2.52 | 67.7% ±7.09 |
| `sft-4b-v2`　自训 LoRA SFT | 68.2% ±0.77 | **70.1%** ±0.76 | 61.0% ±6.70 | 75.0% | 84.4% ±1.96 | 73.8% ±6.68 |
| **`dpo-4b-open`　＋开源偏好 DPO** | **69.1%** ±0.76 | **70.2%** ±0.76 | 61.0% ±6.70 | **78.5%** | **88.6%** ±1.71 | **84.8%** ±5.50 |
| `instruct-2507`　官方对齐版（对照） | 67.7% ±0.77 | 64.2% ±0.80 | **98.5%** ±1.91 | 95.5% | **90.6%** ±1.58 | **85.4%** ±5.40 |

**2026-10-05：四个模型均使用同一判分栈重跑。** 此前 `base-4b` / `sft-4b-v2` / `instruct-2507` 为 10-03 的结果，而判分代码的 4 个模块（`eval.py` / `answer_extract.py` / `engines.py` / `prompts.py`）其后已变更，跨版本并列不成立。当前四行的 `code.scoring_stack_sha` 完全一致。

**HumanEval 应按「未截断口径」解读。** `sft-4b-v2` 有 **57/164** 条写满 512 token 上限而被截断（判错），`dpo-4b-open` 仅 **1** 条。剔除截断样本后为 0.7944 → **0.8466（+5.2pp）**；原始 73.8% → 84.8%（+11.0pp）中有一半来自「不再写不完」。依据本项目的一贯标准（「啰嗦」不应被算作「不会」），对外报告 +5.2pp，+11.0pp 作为附注。

**同一配置重跑的抖动**（两轮全量实测）：MMLU ±0.1pp、GSM8K ±0.5pp、指令遵循 ±0.5pp、HumanEval ±1~4 题（164 题上为 2.4pp）。上述幅度均在置信区间之内，不改变结论；但 0.3pp 的差异不足以判定版本优劣。逐题预测存在 5~15% 的翻转（以 GSM8K 最多）——vLLM 批量推理在 41 路并发之外需排队，调度组成随完成时刻变化。聚合指标稳定，逐题结果不可复现，详见下文「引擎」相关说明。

**结果解读要点：**

1. **MMLU 有两列，不应仅关注 chat 一列。** chat 口径将「答案：」置于 user 回合内，带对话模板的模型会正常作答；而基座模型会将整份提示视为已写完的文档，转而开启下一题——14042 题中有 14035 题未生成任何选项字母。因此 base 的 `0.0%` 并非「不会做题」，而是**该口径对其无效**，其真实水平见「纯文本」一列（更换 chat 包装后由 0% 升至 69.5%，且 0-shot 即可：0/1/2/3/5-shot 实测完全相同）。报告中此类单元格会自动判定为「口径无效」并说明成因。
2. **同口径下三者 MMLU 在 6pp 以内**（69.5 / 70.2 / 64.2）。这符合预期：使用通用指令数据做 SFT 不会提升知识型 MCQ，其改变的是答题格式，而非知识量。因此「base 0% → SFT 68.3%」这类跨口径写法不成立。
3. **GSM8K 的排序为 instruct > SFT > base（91.4 / 83.2 / 68.3）。** 早期版本曾记录「SFT 83.0%，高于官方 instruct 的 51.7%」，该结论错误，成因有两层：GSM8K 仅跑前 400 题，且生成上限设为 **256 token**，而 instruct-2507 输出冗长的 markdown 解题过程，答案在给出前即被截断。改为 1024 token 与全量 1319 题后，其恢复至 91.4%。该问题即「啰嗦」被判为「不会」，为本轮修正的第二个假结论。已确认使用的是 GSM8K **官方 test split**，不存在测试集泄漏。

**主要结论：**

- **SFT 的价值集中在格式与指令，而非知识。** 指令遵循由 39.5% 升至 **61.0%**（+21.5pp，去尾口径 75.0%），而 MMLU 得分离不先学会输出选项字母，二者方向一致。分类看更为明确：代码约束 1/25 → 25/25、禁忌词 19 → 25、结构约束 10 → 20、语言约束 9 → 16。
- **SFT 在数学上确有提升：GSM8K 68.0% → 84.4%（+16.4pp）**，HumanEval 亦上升（67.7% → 73.8%）。差距远大于重跑抖动（GSM8K ±0.5pp / HumanEval ±2.4pp）。
- **DPO 是第二个实质增益，前提是更换数据与目的。** 使用开源 UltraFeedback 中文偏好集（18219 对）在 v2 上再训练一层 LoRA：GSM8K 84.4% → **88.6%**（+4.2pp，为抖动的 8 倍）、HumanEval 73.8% → **84.8%**（未截断口径 +5.2pp）、MMLU 68.2% → **69.1%**（未下降），指令遵循持平（61.0%），且输出更短（ifollow 平均 64.8 → 50.5 token）。代码能力由此追至**与官方 instruct 相差 1 题**（139/164 对 140/164）。
- **与官方 instruct 的剩余差距几乎仅剩指令遵循**（61.0% 对 98.5%）。数学 88.6% 对 90.6%、代码 84.8% 对 85.4% 均已接近。**指令遵循是下一阶段真正需要补齐的部分**（数值约束、格式约束两类已接近满分）。

**说明一：旧 DPO 5 轮全部被否，不代表 DPO 方法无效。** 那 5 轮的数据是为「修复收尾 token」手工构造的定向数据（chosen / rejected 仅相差最后 1 个 token），目的有误，且并非通用偏好数据。改用开源、被广泛复用且非自采样的偏好数据后，第一个 epoch 即取得上述结果。数据转换脚本见 `scripts/make_dpo_open_data.py`（含长度偏置过滤），逐轮失败与根因见上文表格。

**说明二：指令遵循的 61.0% 为保守值，SFT 的真实水平为 75.0%（去尾口径）。** 模型每次回合结束前会生成一个罕见 token（希伯来语词 `לחלוט`，或残缺字节 `\ufffd\ufffd取`），该尾部内容使「字数上限」等规则被违反，200 条中有 30 条因此被误判。报告中提供「去掉尾部乱码后再判」的对照分（`passed_junk_trimmed`），读表时应采用该口径。该缺陷由自训 SFT 引入：仅统计「模型自行决定收尾」的样本，`sft-4b-v2` 有 93.4%（指令遵循）/ 93.0%（GSM8K）/ 92.5%（OpenQA）带该尾部，而 `base-4b` 为 0~2.5%、`instruct-2507` 为 **0.0%**。已查证并非 EOS 监督不足（48000 条样本全部包含 `<|im_end|>`，0 条超长截断，loss 覆盖 EOS），详见 `docs/01-评测.md`；训练侧修该缺陷的 13 次尝试见上文「收尾乱码尾」一节。

交互式报告见[在线版](https://david-dev666.github.io/tiny-post-train/)（GitHub Pages），源码为 `docs/index.html`，与 `evals/results/report.html` 出自同一个 `render()`（自包含、无外部依赖）。评测的执行方式、结果解读与判分过程中已修正的问题，见 [`docs/01-评测.md`](docs/01-评测.md)。

更早一版 **HF 引擎**的结果（仅跑 400 题）存放于 `evals/archive/hf-engine/`，**不参与任何对比**。更换引擎会使绝对分数小幅变动（bf16 下为两条数值路径，实测同一批 50 题逐题预测翻转 13 题），新旧引擎数字并排比较没有意义，因此未在仓库中作为基准保留。报告检测到混合引擎时会直接告警。

### 结果的可信度

报告中另有一张「可信度诊断」表，包含四个指标：**被截断 / 乱码尾 / 兜底抽取 / 口径无效**。这些指标不参与判分，但决定上表是否可用。例如 `--gsm8k-max-new-tokens 256` 会在最终给数之前截断冗长模型的答案（即上文第 3 点修正的问题），从而将**风格差异误判为能力差异**。因此这类信号必须明确披露。

## 硬件与算力

**单卡 RTX 4090 24G**（实测 24564 MiB，driver 580.76.05；宿主 128 核 / 1TB 内存，容器挂 50G 数据盘）。两套 Python 环境相互独立：

| 环境 | 用途 | 关键版本 |
| --- | --- | --- |
| `tpt` | 训练 + HF 引擎推理 | torch 2.12.1+cu130 / transformers 5.5.0 / unsloth |
| `vllm` | 评测（vLLM 引擎） | torch 2.13.0+cu130 / transformers 5.18.0 / vllm 0.30.0 |

两个环境无法合并：vLLM 要求 torch 2.13，unsloth 则固定于 2.12.1，强行合并会破坏训练环境，因此分为两套。

### GPU 小时

| 阶段 | 实测 | 说明 |
| --- | --- | --- |
| SFT 4B · **1 epoch（v2，在用）** | **1.1 h** | 2991 步；LoRA r=32 / 等效 batch 16（micro 4 × accum 4）/ max-seq-len 2048；alpaca-gpt4-zh 约 4.8 万条 |
| SFT 4B · 2 epoch（v1，已弃用） | 2.4 h | 5982 步。eval loss 在约 step 2900 处趋于平稳，第二个 epoch 无额外收益，v2 因此改为 1 epoch |
| 训练冒烟（0.6B） | 0.04 h | 仅验证链路 |
| **vLLM 引擎 · 三模型全量评测** | **0.35 h** | 21 分钟 |
| HF 引擎 · 三模型全量评测 | 2.9 h | 176 分钟，仅作历史记录 |
| 失败重跑与探针 | ~1.5 h（估） | `splitlines` 崩溃、GSM8K token 上限、引擎 A/B 复现性，见 `docs/01-评测.md` 的「判分 bug 史」 |
| 环境搭建 / 下载权重 | 走**无卡模式**，不占用 GPU | 不占 GPU 小时 |

**合计约 9~10 GPU 小时。** 除最后一行外均取自日志实测；该表的用途是考察算力消耗构成，而非精确统计。

### 耗时结构分析

**GPU 时间主要消耗在排查问题，而非训练本身。** 训练仅占 1.1 小时，而排查（判分 bug、token 上限、引擎切换）耗时超过 1.5 小时。仅从训练角度看，这部分投入看似回报有限，但其修正的是**结论本身**（如上文「结果」一节中被推翻的两个假结论），而非少量代码。

**vLLM 将单次全量评测由 2.9 小时缩短至 0.35 小时**，仅为一次训练耗时的 1/3。其价值不在于缩短的时长本身，而在于**决策速度**：评测从需要提前规划变为可随时执行，因节省时间而抽样的动机随之消失。上文 GSM8K 假结论正是抽样与截断共同造成的。
