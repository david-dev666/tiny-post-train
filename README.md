# tiny-post-train

Qwen3-4B 的后训练全流程开源项目：SFT -> DPO -> GRPO -> 评测 -> 部署。

> **在线评测报告（GitHub Pages）**：<https://david-dev666.github.io/tiny-post-train/>

## 目标

在单卡 24G 显存上，用一套可复现的脚本跑通小模型后训练的完整链路，并给出真实评测对比，而不是只贴一个 loss 曲线。

## 流程

| 阶段 | 方法 | 脚本 | 状态 |
| --- | --- | --- | --- |

### 收尾乱码尾：自训 SFT 引入的缺陷，**训练侧 13 次全部证否**

v2 的输出在回合结束前会多吐一个乱码 token（希伯来语词 `לחלוט`、残缺字节 `\ufffd\ufffd取` 这类）。
**只要模型自己决定收尾，就几乎必吐**（自然收尾样本里 92~94%），而 base 只有 0~2.5%、
官方 instruct 是 **0.0%** —— 这个毛病是**自训 SFT 自己引入的**。

靶心已量化：收尾位置 `<|im_end|>` 排第 4，只比第一名乱码低 **0.13 nats**。窗口极小，
但**任何序列级训练信号都落不到这一个点上**。三类机制、共 13 次尝试全部失败：

| 机制 | 轮数 | 代表做法 | 结果 |
| --- | --- | --- | --- |
| SFT 侧 | 6 | 末位 loss / 收尾加权 ×20 / eos 对齐 / 换成模型自生成数据 / 从 Base 重训（v3） | 全否。v3 看似把乱码尾降到 0，实为**「换成不会收尾」**（用满 token 上限 200/200；指令遵循 61.5%→45.0%、GSM8K 83.2%→72.8%） |
| DPO | 5 | 整条序列 / 末位 1-token / eos 对齐 / 第 5 轮 1 epoch + 小 lr | 曲线全健康（`acc` 到 1.0），靶心 logit 只动 **0.06 nats**；`<|endoftext|>` 反被压 5.16 nats |
| RFT | 2 | 拒绝采样（只在自己「答对且干净」的样本上续训） | 第一轮因 3 epoch / lr 1e-4 / 纯 GSM8K 而**停止能力坍塌**；第二轮修掉后不再坍塌，乱码尾**只动了 2~3pp** |

**唯一实测有效的是解码侧**：把 `<|im_end|>` 的 logit 抬 +2.0 → 指令遵循 61.5%→**80.5%**、乱码尾 0。
那是解码技巧、不属于后训练成果，归「阶段 5 推理部署」。

> **一条必须写进验收的判据**：总 `junk_tail` 会被「模型停不下来」刷低 —— v3 和 RFT 第一轮都靠它
> 制造了「指标变好」的假象。任何 adapter 必须同时报三个数：
> **用满 token 上限的样本数** / **自然收尾样本里的乱码尾率** / 主指标。
> 这个坑项目踩了三次 —— 上面表里的 v3 和 RFT 第一轮，都是靠「模型停不下来」把 `junk_tail` 刷低的。

## 实验设计

- 基座：Qwen/Qwen3-4B-Base
- 对照基线：Qwen/Qwen3-4B-Instruct-2507，官方对齐版，用于说明自训流程与官方流程的差距
- 冒烟模型：Qwen/Qwen3-0.6B-Base，用于验证脚本管道，几十分钟就能跑完一轮

从 Base 起步而不是从 Instruct 起步，是为了让 SFT 这一步是真实可控的，整条链路才是完整的后训练。

## 训练看板

训练脚本会把指标追加写到 `outputs/<run>/metrics.jsonl`，看板读这个文件实时画曲线。

```bash
bash scripts/start_dashboard.sh          # 起服务
bash scripts/start_dashboard.sh stop     # 停
bash scripts/start_dashboard.sh token    # 只看口令
```

看板默认跑在 **6006**，并自动生成访问口令（存在 `logs/dashboard.token`，已被 gitignore）。每次启动复用同一个口令，所以手机书签长期有效。

**手机 / 任意设备**：把 AutoDL 实例卡片「自定义服务」里 **6006 那条**域名接上口令打开：

```
https://<你的实例域名>/?token=<口令>
```

**Mac 走 SSH 隧道**（不经过公网，等价可用）：

```bash
ssh -N -L 6006:localhost:6006 autodl
# http://localhost:6006/?token=<口令>
```

看板显示：

| 类别 | 内容 |
| --- | --- |
| 曲线 | train loss、eval loss、perplexity、learning rate、MMLU 子集准确率 |
| 进度 | 当前步数 / 总步数、预计剩余时间 |
| 硬件 | GPU 利用率、显存、温度、功耗 |
| 健康 | 训练进程是否存活 |
| 配置 | 基座模型、数据路径、超参、验证集大小 |
| 数据 | 训练数据抽样 3 条（真实喂进去的样本） |
| 推理 | 固定问题的生成结果（最新 + 上一次对比），附复读率 / 生成长度 |

### 指标说明（别误读）

| 指标 | 含义 | 别当它是 |
| --- | --- | --- |
| `train loss` | 对训练集的拟合程度 | 回答质量 |
| `eval loss` | 对验证集的拟合程度 | 回答质量 |
| `perplexity` | `exp(eval_loss)`，同样只反映拟合度 | 回答质量。**过拟合时它照样降** |
| `复读率` | 生成里重复 2-gram 的占比 | 质量分。只用来发现**退化**（复读率飙升 = 崩了） |
| `词面多样` | 不同 token 的占比 | 质量分。太低说明输出单调 |
| `MMLU 子集准确率` | 固定题目上的多选题正确率 | 综合能力。**用指令数据做 SFT 通常不会提升它，甚至下降**（灾难性遗忘），这是常见现象不是 bug |

**故意没有做的**：不自动算 ROUGE / BLEU，也不给生成结果打质量分。采样的三个问题都是开放式的，没有唯一正确答案，硬套参考答案算出来的数字看着精确、实则误导。真正的效果要看生成结果本身，以及后续 `eval.py` 跑出来的基准评测。

### 基准评测（训练中）

MMLU 全量 14042 题，4B 上跑一遍要一两个小时，比训练还慢，所以用**固定子集**：

```bash
python scripts/bench_subset.py     # 生成 evals/mmlu-subset.jsonl（57 学科 × 8 题 = 456 题）
```

```bash
--bench-every 100                  # 每 100 步在子集上评一次
```

几个要点：

- **子集必须固定**（`--seed` + 只抽一次落盘）。每次重抽的话，题目难度变化会被误读成模型退步。
- **`evals/mmlu-subset.jsonl` 要提交进版本库**，SFT / DPO / GRPO 三阶段的分数才可比。
- 判分只比 A/B/C/D 四个 token 的 logits，不做生成，一次前向就够——所以它测的是「模型更倾向输出哪个字母」，**不等于模型会答题**。
- 国内直连 `huggingface.co` 会超时，脚本默认走 `hf-mirror.com`，可用 `--hf-endpoint` 换。
- 也可以 `--source /path/to/local.jsonl` 完全绕开网络。

### 实时评测指标怎么产生

```bash
--eval-ratio 0.02     # 从训练集切 2% 当验证集（默认）
--eval-steps 50       # 每 50 步评一次
--probe-every 50      # 每 50 步用固定问题采样一次生成，0 表示关闭
```

验证集切分用 `--seed` 固定，**换 seed 曲线就不可比**。

### 关于安全

- 服务**只绑 `127.0.0.1`**。AutoDL 的公网映射转发的是容器内 localhost，所以手机照样能访问，但容器内不会多开一层监听面。
- **口令是必须的**。6006 公网可达，没口令等于把训练数据挂在网上。口令在 URL 里传一次，之后前端存 localStorage 并改用 `X-Token` 请求头。
- 只在隧道场景下想省掉口令：`ENABLE_AUTH=0 bash scripts/start_dashboard.sh`。
- 6008 是另一条映射端口，留给 TensorBoard 用，别和看板抢。

## 结果

**全量口径**（不是抽样）：MMLU 14042 题（两种提问口径各跑一遍）+ 指令遵循 200 条
+ GSM8K 官方 test 1319 题 + HumanEval 164 题。括号内是 Wilson 95% 置信区间半宽（pp）。

**推理引擎 vLLM，三个模型跑完全部只用 21 分钟**（HF 逐条生成要 2 小时 56 分，16.7×）。
换引擎让「跑全量」从一件要计划一晚上的事变成随手就能做的事 —— 上面那批数字是**全量**，
不是抽样，这一点比什么都重要。
**下表全部由同一个引擎产出（vLLM），只有一把尺子**；换引擎要整批重跑。

### ⚖️ 评测公平性：两条硬规则

> **规则一：评测任何模型，都不允许使用任何推理优化或人为技巧干预。**
>
> 禁止：抬高某个 token（如 `<|im_end|>`）的 logits、`logit_bias`、`repetition_penalty` /
> `presence_penalty` / `frequency_penalty`、`bad_words`、`min_tokens` 之类的长度约束、
> 以及任何 `logits_processor` 回调或被 hack 过的 chat template。
>
> 只允许：`temperature=0` 贪心解码、`top_p=1.0`、`max_tokens`、`stop_token_ids`、
> `skip_special_tokens`。（`max_tokens` 是预算不是技巧，但**必须一视同仁并公开** ——
> 见规则二。）
>
> **为什么**：任何解码干预都会把「模型会不会」和「我们让不让它」搅在一起，跨模型对比随即失去意义。
> 本项目吃过这个亏 —— 把 `<|im_end|>` 的 logit 抬高 +2.0，指令遵循能从 61.0% 做到 **80.5%**、
> 乱码尾能做到 **0**，但那是**解码技巧**，模型本身一点没变。所以那批实验（`sft-boost` /
> `probe-boost`）已经从结果目录移进 `evals/archive/`，**不参与任何对比**；补丁代码也已删除，
> `scripts/` 里 grep 不到任何 `logits_processor` / `logit_bias` / penalty 参数。
>
> **规则二：所有参与对比的模型，必须在同一判分栈上重跑过，并且必须公开截断数。**
>
> 判据代码一改，历史数字就不能并列（本项目实测：同一模型换判分栈后 GSM8K 挪动 1.2pp，
> 已 ≥ 重跑抖动 0.5pp）。同时**必须同时报「用满 token 上限的样本数」** ——
> 「写不完」会被误读成「不会」（GSM8K 256-token 那个假结论就是这么来的，
> HumanEval 上 `sft-4b-v2` 有 57/164 条被截断，直接让代码分数虚低 11pp）。

| 模型 | MMLU（chat） | MMLU（纯文本） | 指令遵循 | 指令遵循（去尾） | GSM8K（数学） | HumanEval（代码） |
| --- | --- | --- | --- | --- | --- | --- |
| `base-4b`　Qwen3-4B-Base（基线） | 0.0% ±0.03 | 69.5% ±0.76 | 39.5% ±6.72 | 39.5% | 68.0% ±2.52 | 67.7% ±7.09 |
| `sft-4b-v2`　自训 LoRA SFT | 68.2% ±0.77 | **70.1%** ±0.76 | 61.0% ±6.70 | 75.0% | 84.4% ±1.96 | 73.8% ±6.68 |
| **`dpo-4b-open`　＋开源偏好 DPO** | **69.1%** ±0.76 | **70.2%** ±0.76 | 61.0% ±6.70 | **78.5%** | **88.6%** ±1.71 | **84.8%** ±5.50 |
| `instruct-2507`　官方对齐版（对照） | 67.7% ±0.77 | 64.2% ±0.80 | **98.5%** ±1.91 | 95.5% | **90.6%** ±1.58 | **85.4%** ±5.40 |

> **2026-10-05：四个模型全部用同一判分栈重跑了一遍。** 此前 `base-4b` / `sft-4b-v2` / `instruct-2507`
> 是 10-03 的结果，而判分代码的 4 个模块（`eval.py` / `answer_extract.py` / `engines.py` / `prompts.py`）
> 今天已经不同 —— 跨版本并列是不成立的。现在四行的 `code.scoring_stack_sha` **完全一致**。
>
> **HumanEval 必须按「未截断口径」读**：`sft-4b-v2` 有 **57/164** 条写满 512 token 上限被截断（判错），
> `dpo-4b-open` 只有 **1** 条。剔除截断样本后是 0.7944 → **0.8466（+5.2pp）**；
> 原始的 73.8% → 84.8%（+11.0pp）里有一半来自「不再写不完」。
> 按项目自己的规矩（「啰嗦」不能被算成「不会」），**对外报 +5.2pp**，+11.0pp 当附注。

> **同一配置重跑的抖动有多大**（两轮全量实测）：MMLU ±0.1pp、GSM8K ±0.5pp、
> 指令遵循 ±0.5pp、HumanEval ±1~4 题（164 题上就是 2.4pp）。
> **都在置信区间之内**，不改结论；但别把 0.3pp 的差当成「这版比那版强」。
> 逐题预测会有 5~15% 翻转（GSM8K 最多）—— vLLM 批量推理在 41 路并发之外要排队，
> 调度组成随完成时刻变化。**聚合指标稳，逐题不复现**，下面「引擎」一节有说明。

**读这张表之前必须知道的三件事：**

1. **MMLU 有两列，别只看 chat 那一列。** chat 口径把「答案：」放在 user 回合内，
   带对话模板的模型会正常作答；**基座却把整份提示当成一份已写完的文档，接着去开下一题** ——
   14042 题里有 14035 题一个选项字母都没生成。所以 base 的 `0.0%` 不是「不会做题」，
   而是**这个口径对它无效**，它的真实水平看「纯文本」那一列
   （换掉 chat 包装后 0% → 69.5%，**且 0-shot 就够**：0/1/2/3/5-shot 实测完全一样）。
   报告里这种格子会自动判定「口径无效」并说明成因。

2. **同口径下三者 MMLU 在 6pp 以内**（69.5 / 70.2 / 64.2）。
   这符合预期：**用通用指令数据做 SFT 不会提升知识型 MCQ**，它改的是「按什么格式回答」，
   不是「知道多少」。所以「base 0% → SFT 68.3%」这种跨口径的写法是错的，不要用。

3. **GSM8K 的排序是 instruct > SFT > base（91.4 / 83.2 / 68.3）。**
   早期版本这里写的是「SFT 83.0%，高于官方 instruct 的 51.7%」——**那个结论是错的**，
   成因有两层：GSM8K 只跑了前 400 题，且生成上限被设成 **256 token**，
   而 instruct-2507 写的是啰嗦的 markdown 解题，**答案还没写出来就被截断了**。
   改成 1024 token + 全量 1319 题之后，它回到 91.4%。
   **「啰嗦」被算成了「不会」** —— 这是本轮修正掉的第二个假结论。
   已确认用的是 GSM8K **官方 test split**，不存在测试集泄漏。

**四条真实结论：**

- **SFT 的价值集中在「格式与指令」，不在知识。** 指令遵循 39.5% → **61.0%**（+21.5pp，
  去尾口径 75.0%），而 MMLU 想拿到分本身就依赖先学会「吐一个字母」——这两个方向是同一件事。
  分类别看更清楚：**代码约束 1/25 → 25/25**、禁忌词 19→25、结构约束 10→20、语言约束 9→16。
- **SFT 在数学上真的变强了：GSM8K 68.0% → 84.4%（+16.4pp）**，HumanEval 也涨
  （67.7% → 73.8%）。差距远大于重跑抖动（GSM8K ±0.5pp / HumanEval ±2.4pp）。
- **DPO 是第二个实质增益 —— 前提是换掉数据和目的。** 用开源 UltraFeedback 中文偏好集
  （18219 对）在 v2 上再训一层 LoRA：GSM8K 84.4% → **88.6%**（+4.2pp，是抖动的 8 倍）、
  HumanEval 73.8% → **84.8%**（未截断口径 +5.2pp）、MMLU 68.2% → **69.1%**（不掉），
  指令遵循持平（61.0%），而**输出反而更短**（ifollow 平均 64.8 → 50.5 token）。
  代码能力由此**追到只差官方 instruct 1 道题**（139/164 vs 140/164）。
- **和官方 instruct 的剩余差距几乎只剩指令遵循**（61.0% vs 98.5%）。数学 88.6% vs 90.6%、
  代码 84.8% vs 85.4% 都已逼近。**指令遵循才是下一阶段真正要补的地方**（数值约束 / 格式约束
  两类它仍是接近满分）。

> **旧 DPO 5 轮全否 ≠ 「DPO 不行」。** 那 5 轮的数据是为「修收尾那一个 token」手工构造的定向数据
> （chosen/rejected 只差最后 1 个 token），目的是错的、数据也不是通用偏好数据。
> 换成开源、被广泛复用、且**不是自己采样**的偏好数据后，第一个 epoch 就出了上面的结果。
> 数据转换脚本见 `scripts/make_dpo_open_data.py`（含长度偏置过滤），逐轮失败与根因见上面的表。

> **指令遵循的 61.0% 是保守值，SFT 的真实水平是 75.0%（去尾口径）。**
> 它每次回合结束前会吐**一个**罕见 token（希伯来语词 `לחלוט`，或字节残缺的
> `\ufffd\ufffd取`），那点尾巴把「字数上限」这类规则撑爆了，200 条里有 30 条因此被误判。
> 报告里有「去掉尾部乱码再判」的对照分（`passed_junk_trimmed`），读表时用它。
> **这是自训 SFT 自己引入的缺陷**：只算「模型自己决定收尾」的样本，`sft-4b-v2`
> 有 93.4%（指令遵循）/ 93.0%（GSM8K）/ 92.5%（OpenQA）带它，
> 而 `base-4b` 是 0~2.5%、`instruct-2507` 是 **0.0%**。
> 已查证**不是 EOS 监督不足**（48000 条样本全带 `<|im_end|>`、0 条超长截断、loss 覆盖 EOS），
> 详见 `docs/01-评测.md`；训练侧修它的 13 次尝试见上文「收尾乱码尾」一节。

交互式报告：**[在线版](https://david-dev666.github.io/tiny-post-train/)**（GitHub Pages）
· 源码 `docs/index.html`，与 `evals/results/report.html` 是**同一个 `render()` 的产物**（自包含、零外部依赖）；
**评测怎么跑、怎么读、判分踩过哪些坑，见 [`docs/01-评测.md`](docs/01-评测.md)**。

> 更早那版 **HF 引擎**的结果（只跑了 400 题）存在 `evals/archive/hf-engine/`，**不参与任何对比**。
> 换引擎会让绝对分数小幅变动（bf16 下是两条数值路径，实测同一批 50 题逐题预测翻转 13 题），
> 拿新旧引擎的数字并排看没有意义 —— 所以没在仓库里当基准留着。
> 报告检测到混引擎会直接报警。

### 这张表可信吗

报告里还有一张「可信度诊断」表，四个数：**被截断 / 乱码尾 / 兜底抽取 / 口径无效**。
它们不参与判分，但决定上面这张表能不能用 —— 比如 `--gsm8k-max-new-tokens 256` 会把
啰嗦模型的答案截断在最终给数之前（就是上面第 3 点修掉的那个），
**风格差异会被算成能力差异**，所以这类信号必须摆在明面上。

## 阶段 3：GRPO —— 负结果，第 14 次证否

上面那句「**指令遵循才是下一阶段真正要补的地方**」（61.0% vs 98.5%）不是说说。照着它，用
**GRPO + IF-RLVR**（AI2，arXiv 2507.02833）发起了一次尝试：起点取论文推荐的 `dpo-4b-open`，
奖励用官方口径的「通过约束的比例」（不是 0/1 整题，为的是给组内留梯度）。结果
**主指标 0.0pp（120/200 → 120/200）**，一题没跨过门槛。

两条**能确定**的归因：

1. **奖励形式够不着瓶颈（结构性，实验前就注定）。** 主指标 50 分的缺口全卡在「数值约束 0/25 /
   长度约束 2/25」两类，而这些题的失败方式是**答对了、收尾却多吐一个乱码 token**
   （`72` → `72 לחלוט`），把「纯数字」约束撑爆。GRPO 的奖励是**整条序列的函数**，落不到
   `<|im_end|>` 那**一个 token** 上 —— 这是项目第 **14** 次验证同一件事（SFT 侧 6 + DPO 5 +
   RFT 2 + GRPO 1）。
2. **更新幅度太小。** `lr=1e-6` 是照论文的全参设置抄的，但这里用的是 LoRA（常见 lr 该大 10~100 倍）；
   `kl` 均值 0.0009，策略几乎没偏离起点。

旁证：`junk_tail` 178 → **184**（不降反升）；其他能力（MMLU / GSM8K / HumanEval）全在抖动内，没退化。

**但这轮「方法本身是否有效」判不了 —— 尺子可能拿错了。** 训练用英文约束（IFEval 25 + IFTrain 29），
评测用项目自建的中文模板题，两者不同源；而论文的标准度量 **IFBench**（58 个全新约束、299 条 held-out）
**一条都还没跑**。论文恰恰指出模型会 overfit 到 IFEval 那 25 个模板 —— 训练集 reward 涨到 0.319，
涨的有可能是「模板记忆」，只有 IFBench 能识破。**要判定方法有效与否，唯一的路是补 IFBench。**

完整归因（逐条证据、噪声边界、下一步）：[`docs/02-GRPO尝试.md`](docs/02-GRPO尝试.md)。

## 硬件与成本

**单卡 RTX 4090 24G**（实测 24564 MiB，driver 580.76.05；宿主 128 核 / 1TB 内存，
容器挂 50G 数据盘）。两套 Python 环境互不干扰：

| 环境 | 用途 | 关键版本 |
| --- | --- | --- |
| `tpt` | 训练 + HF 引擎推理 | torch 2.12.1+cu130 / transformers 5.5.0 / unsloth |
| `vllm` | 评测（vLLM 引擎） | torch 2.13.0+cu130 / transformers 5.18.0 / vllm 0.30.0 |

> 装不到一起：vLLM 要 torch 2.13，unsloth 锁在 2.12.1。硬合会把训练搞坏，所以分成两套。

### GPU 小时

| 阶段 | 实测 | 说明 |
| --- | --- | --- |
| SFT 4B · **1 epoch（v2，在用）** | **1.1 h** | 2991 步；LoRA r=32 / 等效 batch 16（micro 4 × accum 4）/ max-seq-len 2048；alpaca-gpt4-zh 约 4.8 万条 |
| SFT 4B · 2 epoch（v1，已弃用） | 2.4 h | 5982 步。eval loss 在 ~step 2900 就走平了，第二个 epoch 是白跑 —— v2 才改成 1 epoch |
| 训练冒烟（0.6B） | 0.04 h | 只验链路 |
| **vLLM 引擎 · 三模型全量评测** | **0.35 h** | 21 分钟 |
| HF 引擎 · 三模型全量评测 | 2.9 h | 176 分钟，仅历史 |
| 失败重跑与探针 | ~1.5 h（估） | `splitlines` 崩溃、GSM8K token 上限、引擎 A/B 复现性 —— 见 `docs/01-评测.md` 的「判分 bug 史」 |
| 环境搭建 / 下权重 | 走**无卡模式**（0.1 元/时） | 不占 GPU 小时 |

**合计约 9~10 GPU 小时。** 除最后一行外都是日志里量出来的；单价按 **¥2/小时** 量级
（项目记录；2026 年外部比价 4090 最低约 ¥2.15/小时）：**总花费约 20 元**。
精确账单以平台后台为准 —— 这张表的用处是看**钱花在哪**，不是对账。

### 这些数字说明了什么

**GPU 时间几乎全花在「试错」上，而不是训练。** 训练只占 1.1 小时，
而排查问题（判分 bug、token 上限、引擎切换）花了 1.5 小时以上 —— 单看训练，这笔账像是浪费；
但那些排查改掉的是**结论本身**（两个假结论被推翻，见上面「结果」一节），不是几行代码。

**vLLM 把「跑一次全量评测」从 2.9 小时压到 0.35 小时**，只占一次训练的 1/3。
它省的不是钱（都是几分钱），是**决策速度**：以前出一个数要计划一晚上，现在随手就跑 ——
于是「为了省时间抽样」这个动机直接消失了。上面那个 GSM8K 假结论正是抽样 + 截断造成的。
