# 评测体系与实战手册

本文档阐明评测系统的**设计原则、判分机制、诊断指标以及工程避坑历史**。详细实现参见 `scripts/eval.py`。

---

## 一、评测设计原则：快、客观、同尺

训练中快照（`--bench-every`）无法提供未经微调的初始基线。独立的离线评测栈提供跨阶段统一、可复现的衡量标准。

| 核心维度 | 实现方式 | 保证机制 |
| --- | --- | --- |
| **快（极致吞吐）** | vLLM 批量推理，3 模型全量 **21 分钟**（HF 引擎需近 3 小时） | 先全量批处理生成文本，后集中判分；非单条串行调用 |
| **客观（程序化判分）** | 无人工介入，无未经校验的裁判模型 | 4 套基准纯程序判定（真实单测执行、正则/数值抽取、硬约束校验）；OpenQA 经严格换位检验 |
| **同尺（单一标准）** | 统一题集、统一生成参数、同一推理引擎 | 产物记录代码与题集指纹；严禁混用引擎拼凑结果 |

### 评测公平性铁律（严禁解码作弊）
所有模型在评测中**严禁使用任何解码侧干预技巧**：禁止人为抬高 `<|im_end|>` 的 logit、禁止 `logit_bias`、禁止重复/长度惩罚参数、禁止 `logits_processor` 回调或魔改 chat template。仅允许 `temperature=0` 贪心解码与公开统一的 `max_tokens` 截断。
> *教训*：推理侧为 `<|im_end|>` 加 2.0 logit 可将指令遵循从 61.0% 虚抬至 80.5%，但这属于部署技巧而非模型能力，混入评测将彻底破坏横向对比基础。

### 引擎边界与复现性特征
1. **统一标尺（vLLM）**：不同推理引擎在 bf16 下数值路径不同（实测 50 题样本中两引擎有 13 题预测翻转）。跨引擎分数不可直接对比，切换引擎必须整批重跑。
2. **聚合指标稳，逐题存在微小翻转**：受 Continuous Batching 调度队列影响，全量重跑时 GSM8K 逐题翻转约 5~15%，但聚合准确率抖动在 ±0.5pp 内，完全落在 95% 置信区间之内。**不可将 <0.5pp 的微小抖动归因为能力差异**。

## 二、五套基准分工与判定机制

所有指标均附带 **Wilson 95% 置信区间**。

| 评测项 | 考察维度 | 判分机制 | 核心认知误区 |
| --- | --- | --- | --- |
| **MMLU（生成式）** | 文本知识与综合理解 | 提取生成文本中的选项字母 | **≠ 综合智商**。通用 SFT 主要调整回答格式，通常不提升甚至微降选择题知识得分（遗忘） |
| **指令遵循 (IF)** | 规则执行硬约束（200 题） | 8 类 24 种格式硬约束程序化打分 | **≠ 内容质量**。仅检验是否严格守住格式/字数/语言等约束 |
| **GSM8K** | 小学数学多步推理（1,319 题） | 提取最终数字比对 | **≠ 泛化推理**。题目与预训练分布高度重合 |
| **HumanEval** | Python 代码生成（164 题） | **真实沙箱执行 + 运行官方单元测试** | **最硬核指标**。单测通过即通过，无任何打分水分 |
| **OpenQA** | 开放式多轮问答 | 裁判模型成对偏好对比（仅用于辅助分析） | **不计入主榜**。存在严重位置偏置，必须经过双向换位校验 |

*注：MMLU 的全词表 logits 判定口径因与 vLLM 引擎不兼容已彻底移除，离线评测统一采用纯粹端到端生成式判定。*

## 三、可信度诊断：看懂真实能力的前提

分数正常并不代表输出健康。评测报表内嵌 4 个关键诊断位，用于识别打分背后的异常：

| 诊断指标 | 定义 | 核心警示与分析 |
| --- | --- | --- |
| **被截断 (truncated)** | 输出触及 `max_tokens` 预算上限 | **不同任务含义截然不同**：GSM8K 截断说明推理未完成（真错误）；HumanEval 截断多为模型自发补写测试用例（真通过） |
| **乱码尾 (junk tail)** | 收尾前吐出冷门/损坏 token | 答案正确但容易因字数/格式硬约束被判错（见下文分析） |
| **兜底抽取 (fallback)** | 触发最宽松规则方提取到答案 | 说明模型输出未按标准格式作答（如复读题干误中选项标号） |
| **口径无效 (unusable)** | 超过 99% 的题目无法提取有效答案 | 模型与当前卷面格式完全不适配，不可用于跨模型横向比对 |

### 1. 乱码尾的本质与溯源
在自训 SFT 模型中，自然收尾样本有 >90% 伴随罕见 token（如词表 id 139941 希伯来语词 `לחלוט` 或字节碎片 `取`）：
- **并非 EOS 监督缺失**：48k 训练数据 100% 显式标注 `<|im_end|>`，全序列计算 Loss，且无超长截断。
- **成因**：模型在学会主动收尾时，在输出 `<|im_end|>` 的前一瞬间概率分布变平，argmax 偶然掉入极低频 token。
- **处置方案**：主指标严格按原始生成判定（不掩盖缺陷）；同时在诊断表提供「去除乱码尾」对照分，直观量化乱码对规则类评测的损耗（指令遵循因此损失约 15pp）。

### 2. 裁判模型的偏置过滤
成对偏好打分（A vs B）天然具备**位置偏置**（实测自对比时，90% 偏向选择第一个选项）。本评测采用**换位双判机制**：仅保留两次判定一致的样本，不一致则判定为平局或剔除，确保评估客观。

## 四、工作流与执行命令

### 1. 全量评测矩阵一键执行
```bash
# 调用 vLLM 独立评测环境运行矩阵
/root/autodl-tmp/envs/vllm/bin/python scripts/eval_pipeline.py \
  --engine vllm \
  --run base-4b=weights/Qwen3-4B-Base \
  --run sft-4b-v2=weights/Qwen3-4B-Base+outputs/sft-4b-v2 \
  --run instruct-2507=weights/Qwen3-4B-Instruct-2507 \
  --mmlu evals/mmlu-full.jsonl --only all

# 生成单页自包含 HTML 评测报表
python scripts/make_report.py
```

### 2. 实用维护命令
- **增量单项更新**：`--update`（沿用历史未变更的评测块，必须限定在同一引擎内）。
- **离线零算力重判**：`python scripts/rescore.py --write evals/results/*.json`（修改解析逻辑或抽取正则后，秒级更新历史结果，无需重新推理）。
- **判分单测回归**：`python tests/test_scoring.py`（CPU 本地快速验证 34 项判分规则与异常处理）。

## 五、MMLU 双口径说明

| 口径 | 卷面设计 | 适用对象 | 机制差异与表现 |
| --- | --- | --- | --- |
| `chat` | 附带对话模板，`答案：` 置于 user 回合内 | 对齐模型 (SFT / Instruct) | 提示被当做标准对话，正常输出选项字母 |
| `plain` | 无包装纯文本 `Question: ... Answer:` | **Base 基座模型** | 基座模型在 `chat` 下会误将输入视作完结文档而复读题干（解析率 0%）；在 `plain` 下无需 few-shot 即可正常发挥（69.5%） |

*工程铁律：严禁进行跨口径对比（如拿基座的 chat 0% 对比 SFT 的 70% 属于严重误导）。*

## 六、工程避坑与判分 Bug 史

判分逻辑错误通常**静默发生**，不会抛出异常中断，仅悄悄污染评测数据。

### 1. 数据解析与文本切分
- **`splitlines()` 截断风险**：Unicode 下包含 `\x85` (NEL)、`\u2028` 等非标换行。MMLU 题库中存在嵌入的 `\x85`，被 `splitlines()` 错误打断导致 JSONDecodeError。**必须使用显式 `split("\n")`**。
- **代码闭围栏正则未容错**：剥离 markdown 围栏时若使用锚定末尾的 `\s*```$`，在遇到末尾乱码 token 时将匹配失败，导致完整代码块包裹进入编译器引发语法错误。**闭围栏必须从首个反引号出现位置后切除，不可锚定末尾**。

### 2. 截断与生成参数陷阱
- **GSM8K 256 Token 虚假低分**：初始参数将最大生成长度设为 256，导致官方 Instruct 模型详细的多步解题链被截断在给出数字之前，分数被压低至 31%。调整为 1024 后恢复至 91%。**风格啰嗦被误判为数学能力缺陷**。
- **Python 代码结构判定放水**：仅使用 `ast.parse` 校验代码合法性，由于 Python 允许中文变量名，纯文本输出可被解析为裸表达式。**必须进一步检查 AST 是否包含函数/类/调用等真实代码节点**。

### 3. 判据收紧与边界保护
- **正则匹配歧义**：原先 GSM8K 匹配末尾 `#### <数字>`，模型直接将提示词中的“数字”视作文本输出（`#### 数字: 18`），导致合法解题被误判。**判据需放宽至末尾合理窗口内识别数值**。
- **告警阈值切勿写成严格相等**：早期「口径无效」判定条件为 `unparsed == total`。样本从 400 题扩展至 14,042 题时，由于 7 道题偶然命中字母，导致告警静默失效。**边界监控必须采用比例阈值判定**。

### 4. 判分栈 SHA 指纹机制
评测产物必须计算并固化包含 `eval.py`、`rules.py`、`code_extract.py`、`engines.py`、`prompts.py` 等全套文件的聚合 SHA-256。只要修改了任何规则或卷面提示，指纹立即变化，杜绝“代码已改但沿用旧成绩”的不公正对比。
