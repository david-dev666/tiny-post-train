# 评测

本文只讲**怎么跑、怎么读、别踩什么坑**。判分实现都在 `scripts/eval.py` 的注释里。

## 为什么单独有一套评测

训练脚本里的 `--bench-every` / `--probe-every` 只能给「训练过程中的快照」，
最早的观测点已经在若干步之后。4B 那次第一颗采样点在 step 100/200，
那时已经训过 1600~3200 条样本 —— **微调前的基线根本不存在**，
所以「这次微调到底有没有用」当时无法回答，只能靠嘴说。

有了 `eval.py`，每个阶段各是一条命令，结果落在 `evals/results/` 直接对照。

## 这套结果站得住吗：快、客观、公正

三个词各有各的落点，分开看：

| | 落在哪里 | 怎么保证的 |
| --- | --- | --- |
| **快** | vLLM 批量推理，三模型全套全量 **21 分钟** | 评测循环是「整项一次生成完再判分」，不是「生成一条判一条」 |
| **客观** | 判分**没有人的主观判断**，也没有裁判模型参与 | 四套是程序化判定（抽字母 / 抽数字 / 逐条查硬约束 / **真跑单测**）；OpenQA 不进主表，单独由裁判做，且剔除「换顺序就翻结论」的样本 |
| **公正** | 三个模型用**同一套题、同一套生成参数、同一个引擎** | 结果 json 记题目指纹 + 生成参数 + 代码指纹；报告检测到题集/引擎不一致会报警 |

**但要说清「公正」的两条边界**：

**边界一：它保证「模型之间可比」，不是「绝对真值」。**
换推理引擎会让绝对分数变动（bf16 下两条数值路径，同一批 50 题逐题预测翻转 13 题），所以：

- **在用的一把尺子 = vLLM。** 表里的数字只能在这一把尺子内部比。
- 旧引擎的结果挪到 `evals/archive/`，**不参与对比**，也不该拿来当「提升/退步」的参考。
- 换引擎 = 整批重跑，不能用 `--update` 把两把尺子的块拼在一起（报告会报警）。

**边界二：同一把尺子重跑，聚合分会小幅抖动。**
同配置同输入跑两轮全量：MMLU ±0.1pp、GSM8K ±0.5pp、HumanEval ±1~4 题。
**都在置信区间内**，跨模型比较不受影响，但「这版比上版高 0.3pp」这种话不能说。
逐题预测会有 5~15% 翻转（详见「引擎」一节的实测表）。

**「快」带来的不只是省时间**：跑全量从「要计划一晚上」变成「随手就能跑」，
于是再也不需要为了省时间抽样 —— 而之前那个 GSM8K 假结论正是抽样 + 截断造成的
（见下面「判分 bug 史」第 4 条）。**能跑全量本身就是评测质量的一部分。**

## 五套评测的分工

| 评测 | 测什么 | 判分方式 | 别拿它当什么 |
| --- | --- | --- | --- |
| MMLU（生成式） | 端到端知识能力 | 生成文本里取选项字母 | 综合智商。**通用指令数据 SFT 不会提升它**，这是常见现象不是 bug |
| 指令遵循 | 听不听话 | 200 条硬约束逐条程序化判分，分 8 类 | 回答质量。它只测「守没守住约束」 |
| GSM8K | 小学数学推理 | 抽答案数字比对 | 泛化推理。题目与训练数据同分布的可能性不低 |
| HumanEval | 写 Python 函数 | **真的执行 + 跑官方单测** | —— 通过了才算会，这个没有水分 |
| OpenQA | 开放式问答 | 本脚本**只收集回答**，判分靠 `judge_openqa.py` 成对偏好 | 自动指标。它需要裁判模型，有位置偏置，脚本会剔除「换顺序就翻结论」的那些 |

**每个准确率都带 95% 置信区间（Wilson）**。全量之后 MMLU 是 ±0.8pp、GSM8K ±2.5pp、
HumanEval ±7.2pp（164 题本来就宽）——只报一个点估计（"68.3%"）会让人以为精确到 0.1pp。
**别拿两个模型 ±0.8pp 的差当结论**：区间重叠就是没差。

> **这里曾经还有第六项：MMLU 的 logits 口径**（只比 `答案：` 后四个字母的 logits、
> 完全不生成）。已移除，别再加回来：它只有 HF 引擎能算（要读**全词表** logits，
> vLLM 只给 top-k logprobs），留着就必然出现「一份 vLLM 结果里嵌一个 HF 算的块」，
> 破掉「整批结果同一把尺子」这条底线。它当初想回答的问题是「基座 MMLU 得 0 分
> 是格式问题还是能力问题」—— 这个已经用 MMLU 两列 + 探针打印的生成原文答完了。
> 训练看板上的 MMLU 曲线仍然是那个口径（见 `notes/dashboard.md`），那是训练过程监控，
> 不进离线评测。

## 一个分数该不该信：看诊断位

**分数对不对是第二位的，「这个分数该不该信」才是第一位的。** 报告里有一张
「可信度诊断」表，四个数：

| 诊断位 | 含义 | 高了说明什么 |
| --- | --- | --- |
| **被截断** | 生成用满了 token 上限 | **含义随评测项不同，别一概而论**（见下） |
| **乱码尾** | 回合结束前吐了稀有 token（`לחלוט` / `аци`） | 答案写对了也可能被「字数上限」这类规则判错 |
| **兜底抽取** | 靠最弱的规则抽出字母/数字 | 这个口径对当前模型可能不适用（比如复读题干时抓到的是选项标号） |
| **口径无效** | 全题一个答案都没抽出来 | 这张卷子它没法作答，**不能拿来做跨模型比较** |
| **去掉尾部乱码后** | 把尾部乱码剥掉再判一遍的对照分 | 和主分数差距大 → 那点乱码值多少分，一眼可见 |

这些都不参与判分 —— 它们是「打分之外的异常」，用来判断上面那张表能不能用。

### 「被截断」在两个评测项里是两件事

| | 截断意味着 | 要不要调大上限 |
| --- | --- | --- |
| **GSM8K** | **答案还没写出来就被切了** → 分数被系统性压低 | **要**（256 → 1024，实测 instruct 从 31% 回到 91%） |
| **HumanEval** | 函数早写完了，模型在**继续写自己的示例调用** | **不用**（实测 512 → 1024 只多 2 题，在抖动内） |

HumanEval 那次专门查过：sft-4b-v2 的 56 条「截断」里 **43 条是在写 `print(...)` / `assert ...` 自测**，
其中 36 条**照样通过**。而且代码抽取本来就在 `\nprint(` 处截断，多写的那段进不了判分。
所以那个数字高只说明模型爱自测（这本身是好事），不代表答案被切掉。

> 教训：**同一个诊断名在不同评测项下可能指着完全不同的事。**
> 看到「截断 56/164」先别急着调大上限 —— 先看被截断的内容是什么。
> GSM8K 那个真问题是「切在答案之前」，不是「用满了上限」。

### 「乱码尾」不是 EOS 监督不足（查过了，别再查一遍）

现象的规模：指令遵循里 base 27/200 → **sft 151/200**，代价是 30 条被误判
（线上 61.5% 对上去掉乱码 76.5%，**差 15pp**）。很容易想到「训练时没监督到 EOS」，
**但实测不是**：

| 查了什么 | 结果 |
| --- | --- |
| 那个 token 是什么 | 词表 **id 139941**，希伯来语词 `ėחלוט`（不是「坏 token」，是罕见的多语言词条） |
| 48000 条训练样本带 `<|im_end|>` 吗 | **全部带**，渲染尾部就是 `…<\|im_end\|>\n` |
| 有样本因超长被截断而丢掉结尾吗 | **0 条**（长度中位 139 token、最大 846，远低于 2048） |
| loss 覆盖 EOS 吗 | **覆盖**（SFTTrainer 用 `text` 字段、默认不 mask，全序列参与 loss） |

**EOS 被监督得很好。** 那 `לחלוט` 哪来的：模型在「内容写完了、该结束回合」那一步
分布摊平，贪心把 argmax 落到了这个低频词上，然后才吐 `<|im_end|>`。
基座就有（27/200），SFT 放大到 151 —— 因为**基座很少主动收尾**（截断 108/200），
SFT 学会收尾之后（截断 19/200），经过那个不稳定位置的机会就多了。
**它是「学会收尾」的副作用，不是新缺陷。**

**处置**：不改判分口径（线上看原始输出，乱码是模型的真实输出），
改用报告里的对照分把它摆到明面上。要根治得从模型侧入手，那是下一阶段（DPO）的事。

### 「去掉尾部乱码后的对照分」怎么用

**主分数一律按原始输出判**：乱码是模型的真实输出，剥掉等于掩盖缺陷。
但差距必须摆出来，否则会被读成能力问题。实测：

```
sft-4b-v2 · 指令遵循   主分数 61.0%
                       乱码尾 151/200（76%）
                       去掉尾部乱码后 77.0%（+16.0%）
```

16pp 的差距来自 `exactly-5-words`（乱码多算一个词）、`numeric-9`（不再是纯数字）、
`len-g03`（超字数）这类**紧约束** —— 答案内容是对的，被 1~3 个 token 判掉。

顺带记：模型的乱码尾率本身就是个质量指标。sft-4b-v2 是 76% / 60% / 52%（三个评测项），
而 base 和 instruct 都是 **0%** —— 说明这是**我们自己的 SFT 训练**引入的缺陷
（`generate()` 的停止逻辑是对的，逐 token 验证过）。

## 怎么跑

### 多模型一条命令跑完，自动出 HTML 报告

```bash
# 默认引擎是 vLLM（快 16.7×）。它装在独立环境里，见下一节
/root/autodl-tmp/envs/vllm/bin/python scripts/eval_pipeline.py \
  --engine vllm \
  --run base-4b=weights/Qwen3-4B-Base \
  --run sft-4b-v2=weights/Qwen3-4B-Base+outputs/sft-4b-v2 \
  --run instruct-2507=weights/Qwen3-4B-Instruct-2507 \
  --mmlu evals/mmlu-full.jsonl --only all

python scripts/make_report.py     # → evals/results/report.html（自包含，零外部依赖）
```

- `--run` 格式：`标签=模型路径[+adapter路径]`。用 `+` 而不是 `:`，因为路径里带冒号的情况更多
- 默认**跳过已完成的结果**，方便断点续跑；要重跑加 `--force`。
  **「已跑过」的判定包含引擎** —— 一份 HF 的结果不会被当成「vLLM 跑过了」而跳过
- `--parallel`：**vLLM 恒为 1**，它单进程就能喂满卡。HF 路径相反，单进程时 GPU 利用率只有 9%
  （batch=1 是延迟瓶颈），那时 `--parallel 2` 反而把卡喂满（实测 17G / 98%）

### 引擎：vLLM 是唯一在用的那把尺子

| | vLLM（`--engine vllm`，在用） | HF（`--engine hf`，备用） |
| --- | --- | --- |
| 解释器 | `/root/autodl-tmp/envs/vllm/bin/python`（torch 2.13） | `tpt` 环境（unsloth / torch 2.12.1） |
| 速度 | **0.57 s/题** | 9.43 s/题 |
| 可复现 | 聚合稳（±0.5pp 内）、**逐题不复现**（见下） | 逐条确定 |

**vLLM 为什么快**：它把整批题一次交给 continuous batching 调度。所以
`eval.py` 里的评测循环是「**先把这一项的所有卷面拼好一次性生成，再逐条判分**」，
而不是原来的「生成一条判一条」—— 逐条调用等于每条自成一个 batch，加速全没了。
HF 后端内部仍是逐条，行为与换引擎前逐字节一致（备用/对照用）。

**只有一把尺子。** 换引擎不是调个参数：bf16 下 HF 与 vLLM 是两条数值路径，
同一批 50 题逐题预测有 **13 题翻转**（文本 32 题不同，聚合分差 3 题）——
不是「谁更准」（方向两边都有），是自回归误差发散。
所以**换引擎要整批重跑，新旧引擎的分数不能并排看**。
结果 json 记 `engine` / `engine_config`；`eval_pipeline` 把引擎纳入「是否已跑过」的判定；
报告检测到混引擎会报警。旧的 HF 结果已挪到 `evals/archive/`，不参与任何对比。

#### 可复现到什么程度（实测，别过度概括）

**`enforce_eager` 是必须的，但它只解决一半问题。** 关掉 CUDA graphs 之后，
**小批量**下确实逐字相同（50 题 GSM8K 跑两遍：预测/文本/token 数全同，0 差异）——
原因是 50 条序列能**全部同时在跑**，调度组成从头到尾不变。

但**全量跑不是这样**。同配置、同代码、同输入跑两轮全量（1319 / 200 / 164 题）：

| 评测项 | 逐题预测翻转 | 聚合分变化 |
| --- | --- | --- |
| 指令遵循（200） | 0 | 0 |
| HumanEval（164） | 0 | ±1~4 题（≤2.4pp） |
| MMLU chat（14042） | 0 ~ 150 | ≤±0.1pp |
| MMLU 纯文本（14042） | 125 ~ 211 | ≤±0.1pp |
| GSM8K（1319） | **74 ~ 197** | **≤±0.5pp** |

两条规律：

1. **输出越长，翻转越多。** 指令遵循 / HumanEval 的输出被停止符短促截断 → 0 翻转；
   GSM8K 要生成上千 token 的推理链 → 15% 翻转。这是自回归误差累积的直接体现。
2. **聚合分抖动都落在置信区间内**（MMLU ±0.8pp、GSM8K ±2.5pp），
   所以「模型之间比高低」不受影响 —— 但**别把 0.3pp 的差当结论**。

**根因**：GPU 上只有约 41 路并发（`GPU KV cache size: 84,128 tokens / 2048`），
1319 条题必须排队。每一步实际组成哪一批，取决于当时哪些序列还没写完 ——
调度组成的微小差异会让 GEMM 形状变，bf16 下 argmax 偶尔翻转，然后放大。

> **代价要说清**：vLLM 换来的是 16.7× 速度 + 聚合稳定，不是逐题可复现。
> 想逐题复现只能把并发压到很小（大批题目根本放不下），速度就没了 —— 不划算。
> 上一版文档在这里写过「逐字相同」，那是在 **50 题**上验的结论，
> 被直接推广到了全量 —— 样本量不足导致的过度概括，已记入失败记录。

> 两个环境坑已在 `engines._prepare_env()` 里绕掉：调用方不激活环境时 `ninja` 不在 PATH
> （flashinfer 要现场编译）；本机 nvcc 是 CUDA 12.4，编不了 flashinfer 0.6.18 要的
> `--compress-mode`，所以关掉 flashinfer 采样核。

### 成本参考（RTX 4090 24G）

三模型总耗时，全套全量（MMLU 14042 × 两口径 + GSM8K 1319 + HumanEval 164 + 指令遵循 200）：

| 引擎 / 配置 | 三模型总耗时 |
| --- | --- |
| **vLLM，全量（现在的默认）** | **21 分钟**（base 5.9 / sft 8.7 / instruct 5.9） |
| HF，全量，串行 | 约 12.5 小时（GSM8K 一家占 2/3） |
| HF，`--limit 400` 截断档 | 约 2 小时 |

而截断档正是 GSM8K 那个假结论（见下「判分 bug 史」第 4 条）的来源：
**当跑全量变得便宜，就不该再为了省时间抽样。**

### 只补跑一项：`--update`

```bash
python scripts/eval.py --engine vllm --model weights/Qwen3-4B-Base --label base-4b \
  --only mmlu --mmlu-style both --mmlu evals/mmlu-full.jsonl --update

沿用来的块会记进 `carried_over`，报告里标「N 块沿用上次」——

## MMLU 有两个口径，别搞混

| 口径 | 卷面 | 给谁用 |
| --- | --- | --- |
| `chat` | 带对话模板，`答案：` 在 **user 回合内** | 指令微调过的模型 |
| `plain` | 纯文本 `Question: … Answer:`，无 chat 包装 | **基座** |

`chat` 口径下模型真正开始生成时已经另起 `<|im_start|>assistant` 回合。
instruct 模型知道「assistant 该回答」，**基座不知道** —— 它把「答案：」+ 回合结束符
理解成「这是一份写完的文档」，于是接着**开下一题**（复读题干）：

```
chat  口径  →  0/400  全体解析不出字母
plain 口径  →  281/400 = 70.2%
```

而且**不需要 few-shot**：`plain` 口径下 0/1/2/3/5-shot 完全一样（都是 17/20）。

**「base 0% → SFT 70.8%」这种写法是错的**，它量的是格式适配，不是知识能力。

## 判分 bug 史（都别改回去）

### 1. JSONL 用 `str.splitlines()` 切开

`splitlines()` 按 Unicode 定义的**所有**行边界切分，包括 `\x85`(NEL) / `\x0b` / `\u2028`，
而 JSONL 的换行只是 `\n`。MMLU 题库第 6956 行含一个 `\x85`，那一行被从 JSON 字符串
中间切开，直接 `JSONDecodeError`，整个评测崩掉。

**用 `split("\n")`。** 踩坑的更深一层：本地校验脚本用 `for line in f`、
线上用 `splitlines()`，两边切法不同，**校验通过而线上必崩**。

### 2. 闭围栏正则锚定 `$`

原来剥代码围栏写的是 `re.sub(r"\s*```$", "", text)`，`$` 要求围栏在字符串**最末尾**。
而模型输出是：

    ```python
    def reverse_string(s):
        return s[::-1]
    ``` לחלוט

围栏后面还跟着乱码 token，`$` 匹配不上 → 围栏没剥掉 → 拼出来的程序第一行是 ```` ``` ````
→ SyntaxError。164 题里挂了 80 题，**真实 73.2% 被压成 35.4%**，
差点得出「SFT 把代码能力练废了」这个完全相反的结论。

**闭围栏要从它出现的位置起全部丢弃，不锚定末尾。**

### 3. 只取「第一个 A-D」（MMLU）

原来 `LETTER_RE.search()` 取生成文本里**第一个** A/B/C/D。模型一旦复读题干，
第一个字母就是选项标号 `A.` 而不是答案 —— 于是出现「出字母 20/20 但只有 10% 正确」
这种假分数。现在按「整体就是字母 > 以字母开头 > 带标记 > 兜底」分级抽取，
并统计各规则命中数（兜底占比高 = 这个口径不可信）。

### 4. GSM8K 的 token 上限给太小

`--gsm8k-max-new-tokens` 默认 256 时，**啰嗦的模型答案会被截断在最终给数之前**，
「抽最后一个数字」抽到中间值。同一个 16 题样本：

| 模型 | 256 token | 1024 token | 被截断 |
| --- | --- | --- | --- |
| base-4b | 50.0% | 62.5% | 6/16 → 1/16 |
| sft-4b-v2 | 87.5% | 87.5% | 0/16 → 0/16 |
| instruct-2507 | **31.2%** | **87.5%** | **11/16** → 0/16 |

**风格差异被算成了能力差异。** 现在默认 1024，并且诊断表会报截断率。

---

### 5. `python_code` 只判断「能 parse」

Python 的标识符**允许中文**，所以「这不是代码」能 `ast.parse` 成功
（解析成一个裸 `Name` 表达式）—— 于是纯文本被判成合法代码。
现在要求 AST 里必须出现函数定义 / 调用 / 赋值这类**代码结构**才算过。

### 6. `follows_hash_format` 的判据写窄了

原来要求「最后一行严格等于 `#### <数字>`」。实测两个模型都写成：

```
base          #### 数字
              18
sft           #### 数字: 18. (Janet makes $18 ...)
```

它们**把提示里的「数字」当成了字面量**（提示词 `用「#### 数字」的格式` 确实有歧义）。
结果 sft 显示「按格式作答 0/400」，看起来像完全没照做，其实是判据错。
现在改成「末尾 120 字内 `####` 后跟数字」，并要求**后面有数字**（把基座的
`#### 1. 计算…` 这种章节编号排除掉）。

> 提示词那个歧义**记下但没改** —— 改它要重跑全部 GSM8K，而判分并不依赖格式
> （`last_number` 保证「只要写了数字就能判对」）。列为已知待办。

### 7. `_lines()` 也在用 `splitlines()`

和 JSONL 那次同源：`splitlines()` 按 Unicode 定义的**所有**行边界切，
`\x85` / `\u2028` / `\x0b` 都会被当换行。影响 `single_line` / `line_count_eq` /
`starts_with` / `line_prefix_count` / `line_starts_with_all` 五种规则。

实测 200 条指令遵循输出里 **0 条**含这类字符，所以是**潜伏** bug（不像 JSONL 那次真炸了），
但规则里「只输出一行」「恰好 3 行」会因此误判。

### 8. `line_prefix_count` 用的是「至少」

题面全是「用**三个**要点…」，规则却写成 `n >= rule["n"]` —— 给 5 个要点照样判通过。
对啰嗦模型是放水（sft-4b-v2 正是啰嗦的那个）。实测当前 0/7 触发，改了分数不变，但口径对了。

### 9. 「口径无效」告警写成严格相等，样本一变大就失效

报告会在「某个模型在某个口径下抽不出答案」时标出「口径无效」——
比如基座用 chat 口径做 MMLU，它把提示当成已写完的文档接着往下写，一个选项字母都不吐。

判定原先写的是 `unparsed == total`。**400 题时恰好成立**（干净的 400/400），
换成全量 **14042 题**之后是 **14035/14042** —— 有 7 条碰巧吐出了字母。
严格相等当场落空，**告警从报告里消失了**，而表上那一格照样是醒目的 `0.0%`。
这恰恰是最容易被误读成「模型不会做题」的格子。

改法：阈值按**比例**判（解析失败率 ≥ 99%，`UNUSABLE_UNPARSED_RATIO`），
并在说明里写出真实比例而非含糊的「全部」。

> 教训：**边界条件不要写成严格相等。**「全部失败」「全部截断」这类判断，
> 样本一变大几乎必然出现零星例外，写等值等于把告警绑死在某个特定样本量上。
> 报告里同样是「比例报警」的截断率（`TRUNCATION_ALARM = 0.20`）就一直工作正常。

### 10. 「截断档」告警读的字段从来没被写过

`make_report.py` 判断一份结果是不是 `--limit` 截断档，读的是 `requested["limit"]`。
但 `eval.py` 写 `requested` 时只放了 `only` / `mmlu_style`（当时还带着一个 logits 口径开关，现已移除），**从来没有 `limit`**。
于是这个告警是一段死代码：一批只跑了前 400 题的结果，在页面上和全量结果长得一模一样。

改法：`eval.py` 的 `requested` 加上 `limit`（没截断时写 `None`）。

> 这类 bug 不会报错，也不会让任何数字变错 —— 它只是**让一个保护措施静默失效**。
> 报告里的告警都得有一个「构造出触发条件」的验证，否则不知道它还在不在工作。

## 判分栈指纹：改了规则必须能被发现

结果 json 里记 `code.scoring_stack_sha` —— **整个判分栈**的聚合指纹：

```
eval.py（流程）  rules.py（24 种规则判定）  metrics.py（置信区间 + 退化指标）
answer_extract.py（数字/字母抽取）  code_extract.py（剥围栏）
prompts.py（卷面原文）  engines.py（生成参数）  train_sft.py（停止符）
```

**为什么必须覆盖全部**：判分逻辑拆成多个文件之后，只记 `eval.py` 的 sha 会出现
「改了 `rules.py`（也就是改了判分规则），指纹一点不变」—— 两份结果会声称
同一版代码，实际用的判定引擎不同。这正是指纹存在的唯一理由。

`prompts.py` 也在内：它供给 GSM8K / 代码题的**卷面原文**，改一个字的措辞分数就可能变 ——
那是比判分更上游的变量。`engines.py` 同理：生成参数（采样、停止符截断语义）在那里。

补跑脚本里还有一道护栏：开跑前记一次 `scripts/*.py` 的 md5，跑完再对一次，
中途被改就打印警告。**跑批期间不要动 `scripts/` 下任何文件** ——
需要改就改完重跑，别指望「跑完再补一次重判」（那会让盘上留的代码和实际跑的代码不是同一版）。

## 反面教材：两个「被修坏」的尝试

上面四个是真 bug，下面两个是我在排查时**误判**出来的，记下来免得后人再走一遍：

**（1）以为 `$80,000` 会被拆碎。** 实测不会 —— `make_benchmarks.last_number` 的正则
本来就带千分位。我当时的「证据」是用自己临时敲的正则跑出来的，不是线上代码。

**（2）以为该「优先取 `####` 后面的数字」。** 实测更差：**基座把 `####` 当章节编号用**
（`#### 1. 计算每天的总产蛋量`），改成标记优先后基座从 55.8% 掉到 45.2%。
四种候选规则全测了一遍，现状（全文最后一个数字）最好，所以**不动**。

教训：**改判分逻辑之前，先在存档数据上把候选规则都跑一遍。**
「看起来更严谨」的规则经常更差，而判分 bug 不会报错。
