# 评测

本文只说明评测的执行方式、结果解读方法以及需要规避的问题。判分实现见 `scripts/eval.py` 的注释。

## 为什么单独有一套评测

训练脚本中的 `--bench-every` / `--probe-every` 只能提供训练过程中的快照，最早的观测点已在若干步之后。4B 训练中第一个采样点位于 step 100/200，此时已训练 1600~3200 条样本，微调前的基线并不存在，因此当时无法回答「本次微调是否有效」，只能依赖主观判断。

使用 `eval.py` 后，每个阶段各对应一条命令，结果写入 `evals/results/`，可直接对照。

## 结果的可信度基础：快、客观、公正

三者各有侧重：

| | 落在哪里 | 保障方式 |
| --- | --- | --- |
| **快** | vLLM 批量推理，三模型全套全量 **21 分钟** | 评测循环采用「整项一次生成完再判分」，而非「生成一条判一条」 |
| **客观** | 判分不包含主观判断，也无裁判模型参与 | 四套为程序化判定（抽取字母 / 抽取数字 / 逐条检查硬约束 / **实际执行单元测试**）；OpenQA 不进主表，由裁判单独完成，并剔除「交换顺序即改变结论」的样本 |
| **公正** | 三个模型使用同一套题、同一套生成参数、同一个引擎 | 结果 json 记录题目指纹、生成参数与代码指纹；报告检测到题集或引擎不一致时会告警 |

「公正」有两条边界需要说明：

**边界一：它保证模型之间可比，而非绝对真值。**
更换推理引擎会使绝对分数变动（bf16 下存在两条数值路径，同一批 50 题逐题预测翻转 13 题），因此：

- **在用的唯一尺子为 vLLM。** 表中的数字只能在该尺子内部比较。
- 旧引擎的结果已移至 `evals/archive/`，**不参与对比**，也不应作为「提升/退步」的参考。
- 更换引擎需整批重跑，不能用 `--update` 将两把尺子的结果拼接（报告会告警）。

**边界二：同一尺子重跑时，聚合分会小幅抖动。**
相同配置与输入运行两轮全量：MMLU ±0.1pp、GSM8K ±0.5pp、HumanEval ±1~4 题。上述幅度均在置信区间内，不影响跨模型比较，但不能据此判定「某版本比另一版本高 0.3pp」。逐题预测存在 5~15% 的翻转（详见「引擎」一节的实测表）。

**「快」的意义不止于节省时间**：全量评测从需要提前规划变为可随时执行，因此不再需要为节省时间而抽样；此前的 GSM8K 假结论正是抽样与截断共同造成的（见「判分 bug 史」第 4 条）。**能够运行全量本身即是评测质量的一部分。**

## 五套评测的分工

| 评测 | 测什么 | 判分方式 | 不代表 |
| --- | --- | --- | --- |
| MMLU（生成式） | 端到端知识能力 | 从生成文本中抽取选项字母 | 综合智力。通用指令数据 SFT 不会提升该指标，属常见现象而非缺陷 |
| 指令遵循 | 是否遵从约束 | 200 条硬约束逐条程序化判分，共 8 类 | 回答质量。仅衡量「是否守住约束」 |
| GSM8K | 小学数学推理 | 抽取答案数字比对 | 泛化推理。题目与训练数据同分布的可能性较高 |
| HumanEval | 编写 Python 函数 | **实际执行并运行官方单元测试** | —— 通过方计为掌握，无主观成分 |
| OpenQA | 开放式问答 | 本脚本仅收集回答，判分由 `judge_openqa.py` 成对偏好完成 | 自动指标。需要裁判模型，存在位置偏置，脚本会剔除「交换顺序即改变结论」的样本 |

**每个准确率均附带 95% 置信区间（Wilson）。** 全量下 MMLU 为 ±0.8pp、GSM8K ±2.5pp、HumanEval ±7.2pp（164 题的区间本身较宽）。仅报告点估计（如「68.3%」）会让人误以为精确到 0.1pp。**不应将两个模型 ±0.8pp 的差异视为结论**：区间重叠即无差异。

以下两点为已确立的约定：

**其一，曾设置的第六项「MMLU 的 logits 口径」已移除，不应重新引入。** 该口径仅比较 `答案：` 后四个字母的 logits，完全不生成。它只有 HF 引擎可计算（需读取全词表 logits，而 vLLM 仅提供 top-k logprobs），保留它必然导致「一份 vLLM 结果中嵌入一个 HF 计算的块」，破坏「整批结果同一把尺子」这一底线。该口径原本用于回答「基座 MMLU 得 0 分是格式问题还是能力问题」，现已通过 MMLU 两列与探针打印的生成原文回答。训练看板上的 MMLU 曲线仍采用该口径（见 `dashboard/server.py`），但其属于训练过程监控，不进入离线评测。

**其二，评测公平性硬规则**（完整表述见 README 的「评测公平性：两条硬规则」一节）：离线评测**不允许任何推理优化或人为技巧干预**，包括抬高特定 token（如 `<|im_end|>`）的 logits、`logit_bias`、`repetition_penalty` / `presence_penalty` / `frequency_penalty`、`bad_words`、长度约束、`logits_processor` 回调，全部禁止；仅允许贪心解码与 `max_tokens`、`stop_token_ids`、`skip_special_tokens`。任何解码干预都会混淆「模型是否具备该能力」与「是否允许其表现」，跨模型对比随即失去意义。本项目曾产生此类反例（将 `<|im_end|>` 的 logit 提高 +2.0，指令遵循由 61.0% 升至 80.5%、乱码尾降至 0），该批结果已移入 `evals/archive/`，不参与任何对比。

## 如何判断一个分数是否可信：诊断位

**相比分数是否正确，更优先的问题是「该分数是否可信」。** 报告中另有一张「可信度诊断」表，包含以下指标：

| 诊断位 | 含义 | 偏高的含义 |
| --- | --- | --- |
| **被截断** | 生成用满了 token 上限 | **含义随评测项不同，不可一概而论**（见下） |
| **乱码尾** | 回合结束前生成了稀有 token（`לחלוט` / `аци`） | 答案即使正确，也可能因「字数上限」等规则被判错 |
| **兜底抽取** | 依靠最弱的规则抽取字母或数字 | 该口径对当前模型可能不适用（例如复读题干时抓取到选项标号） |
| **口径无效** | 全部题目均未抽取到答案 | 该模型无法按此口径作答，**不可用于跨模型比较** |
| **去掉尾部乱码后** | 剥离尾部乱码后重新判分的对照分 | 与主分数差距较大时，说明该乱码的影响可直接量化 |

以上指标均不参与判分，属于判分之外的异常信号，用于判断上表是否可用。

### 「被截断」在两个评测项中含义不同

| | 截断的含义 | 是否应调大上限 |
| --- | --- | --- |
| **GSM8K** | **答案尚未写出即被截断**，分数被系统性压低 | **应调大**（256 → 1024，实测 instruct 由 31% 回升至 91%） |
| **HumanEval** | 函数已写完，模型在继续编写自己的示例调用 | **不必**（实测 512 → 1024 仅多 2 题，处于抖动范围内） |

HumanEval 曾专门核查：`sft-4b-v2` 的 56 条「截断」中有 **43 条是在编写 `print(...)` / `assert ...` 自测**，其中 36 条**仍然通过**。此外代码抽取本就在 `\nprint(` 处截断，多写的部分不进入判分。因此该数值偏高仅说明模型习惯自测（这本身是良性行为），并不代表答案被截断。

应记录的经验：**同一诊断名称在不同评测项下可能指向完全不同的问题。** 见到「截断 56/164」时不应立即调大上限，而应先检查被截断的内容。GSM8K 的实际问题是「截断发生在答案之前」，而非「用满了上限」。

### 「乱码尾」不是 EOS 监督不足（已核查，无需重复）

现象规模：指令遵循中 base 为 27/200，**sft 为 151/200**，代价是 30 条被误判（原始口径 61.5%，去掉乱码后 76.5%，**相差 15pp**）。由此容易推断「训练时未监督到 EOS」，**但实测并非如此**：

| 核查项 | 结果 |
| --- | --- |
| 该 token 是什么 | 词表 **id 139941**，希伯来语词 `ėחלוט`（并非异常 token，而是罕见的多语言词条） |
| 48000 条训练样本是否包含 `<|im_end|>` | **全部包含**，渲染尾部为 `…<\|im_end\|>\n` |
| 是否有样本因超长被截断而丢失结尾 | **0 条**（长度中位数 139 token、最大值 846，远低于 2048） |
| loss 是否覆盖 EOS | **覆盖**（SFTTrainer 使用 `text` 字段、默认不 mask，全序列参与 loss） |

**EOS 得到了充分监督。** `לחלוט` 的来源为：模型在「内容已写完、应结束回合」这一步分布摊平，贪心解码将 argmax 落在该低频词上，随后才生成 `<|im_end|>`。基座模型即存在该现象（27/200），SFT 将其放大至 151 —— 原因是基座很少主动收尾（截断 108/200），而 SFT 学会收尾后（截断 19/200），经过该不稳定位置的机会增多。**它是「学会收尾」的副作用，而非新增缺陷。**

**处置**：不修改判分口径（线上以原始输出为准，乱码是模型的真实输出），改为在报告中提供对照分以明确披露。根治需从模型侧入手，属下一阶段（DPO）的工作。

### 裁判本身是否可信（已实测）

成对偏好（OpenQA 裁判、构造 DPO 数据）均依赖同一假设：**裁判确实在比较内容**。该假设值得实测，方法是让裁判对「同一份答案与它自身」进行比较：

| 输入 | 判定结果 | 说明 |
| --- | --- | --- |
| A vs A（完全相同） | **判定为「一」27/30**、平局 3/30 | **明显的位置偏置**：内容无差异时 90% 选择第一个 |
| A vs A + 一句冗余内容 | 加长的一份获胜 **0/30** | **不存在长度偏置**（提示词中「更长不等于更好」确实生效） |

因此裁判的偏置结构为「**位置 > 内容 > 长度**」，其中位置偏置由换位机制消除：纯位置驱动的判定会两次结果不一致，从而被丢弃。实测 30 对中仅丢弃 2 对，说明在真实样本中内容差异压过了位置偏置，换位过滤有效；但它会丢弃全部「内容差异本就不大」的样本，因此**保留下来的样本均偏向「差距悬殊」**，在解读「保留率」时需注意这一点。

该结论同样适用于 DPO 数据：构造的偏好对中 chosen 与 rejected 的差距偏大，训练信号较强，但这也意味着模型学到的是「明显的优劣」，而非「细微的好坏」。

### 「去掉尾部乱码后的对照分」的使用方式

**主分数一律按原始输出判定**：乱码是模型的真实输出，剥离等于掩盖缺陷。但差距必须明确披露，否则会被解读为能力问题。实测（vLLM 全量）：

```
sft-4b-v2 · 指令遵循   主分数 61.5%（123/200）
                       乱码尾  169/200（84.5%）
                       去掉尾部乱码后 76.5%（+15.0pp）
```

15pp 的差距来自 `exactly-5-words`（乱码被计入词数）、`numeric-9`（不再是纯数字）、`len-g03`（超出字数）等**紧约束** —— 答案内容正确，仅因**末尾 1 个 token** 被判定不通过。`数值约束 0/25` 整类几乎全部失败（其中 18 条由乱码导致：`'56.פייסב'`、`'1024. לחלוט'`）。

附记：乱码尾率本身即为一项质量指标。**必须仅统计「模型自行决定收尾」的样本**（被截断的题目必然没有乱码尾，实测 0/19、0/10、0/56，因其被预算截断，并未进入「收尾决策」；若不剔除会将截断率混入）：

| 模型 | 指令遵循 | GSM8K | HumanEval | OpenQA |
| --- | --- | --- | --- | --- |
| `sft-4b-v2`（自训） | **93.4%** | **93.0%** | **86.1%** | **92.5%** |
| `base-4b` | 1.1% | 0.0% | 0.0% | 2.5% |
| `instruct-2507` | **0.0%** | **0.0%** | **0.0%** | **0.0%** |

这说明该缺陷由本项目的 SFT 训练引入，而非模型家族的固有问题（`generate()` 的停止逻辑正确，已逐 token 验证）。

### 乱码 token 有两种形态，第二种曾被长期遗漏

1. **其它文字系统**：希伯来语词 `לחלוט`、`פייסב`，或西里尔字母 `ож`、阿拉伯语
2. **U+FFFD 替换字符**：字节级 BPE 的残缺片段。某个 token 的原始字节形如 `A0 A1 E5 8F 96`，独立解码时前两个无效字节变为 `��`、后三个正常解出 `取`，于是**整块解码为 `��取`** —— 它以正常汉字收尾，因此 `[乱码字符]+$` 之类的文本正则**无法匹配、无法剪除**，只能回到 token 层判定（`answer_extract.trailing_junk_len`）

旧检测器仅覆盖第 1 种，导致乱码尾被系统性低估：GSM8K 报告为 65.3%（实际 92.3%）、指令遵循报告为 75.5%（实际 84.5%）。`rescore.py` 为文本层重判，补出的仍为下界；新结果中的 `junk_tokens` 字段按 token 计量，该口径才准确。

## 如何运行

### 多模型一条命令跑完，自动生成 HTML 报告

```bash
# 默认引擎为 vLLM（快 16.7×），其安装在独立环境中，见下一节
/root/autodl-tmp/envs/vllm/bin/python scripts/eval_pipeline.py \
  --engine vllm \
  --run base-4b=weights/Qwen3-4B-Base \
  --run sft-4b-v2=weights/Qwen3-4B-Base+outputs/sft-4b-v2 \
  --run instruct-2507=weights/Qwen3-4B-Instruct-2507 \
  --mmlu evals/mmlu-full.jsonl --only all

python scripts/make_report.py     # → evals/results/report.html（自包含，无外部依赖）
```

- `--run` 格式：`标签=模型路径[+adapter路径]`。使用 `+` 而非 `:`，因为路径中包含冒号的情况更常见。
- 默认**跳过已完成的结果**，便于断点续跑；需重跑时加 `--force`。**「已跑过」的判定包含引擎** —— 一份 HF 结果不会被当作「vLLM 已跑过」而跳过。
- `--parallel`：**vLLM 恒为 1**，其单进程即可喂满 GPU。HF 路径相反，单进程时 GPU 利用率仅 9%（batch=1 构成延迟瓶颈），此时 `--parallel 2` 反而可喂满（实测 17G / 98%）。

### 引擎：vLLM 是唯一在用的尺子

| | vLLM（`--engine vllm`，在用） | HF（`--engine hf`，备用） |
| --- | --- | --- |
| 解释器 | `/root/autodl-tmp/envs/vllm/bin/python`（torch 2.13） | `tpt` 环境（unsloth / torch 2.12.1） |
| 速度 | **0.57 s/题** | 9.43 s/题 |
| 可复现性 | 聚合稳定（±0.5pp 内）、**逐题不可复现**（见下） | 逐条确定 |

**vLLM 速度较快的原因**：它将整批题目一次性交给 continuous batching 调度。因此 `eval.py` 的评测循环为「**先拼好该项目的全部卷面并一次性生成，再逐条判分**」，而非原先的「生成一条判一条」—— 逐条调用会使每条自成一个 batch，加速效果全部丧失。HF 后端内部仍为逐条处理，行为与更换引擎前逐字节一致（用作备用与对照）。

**只有一把尺子。** 更换引擎并非调整参数：bf16 下 HF 与 vLLM 是两条数值路径，同一批 50 题逐题预测有 **13 题翻转**（文本 32 题不同，聚合分差 3 题）——这并非「哪个更准」（两个方向均存在），而是自回归误差发散。因此**更换引擎需整批重跑，新旧引擎的分数不可并排比较**。结果 json 记录 `engine` / `engine_config`；`eval_pipeline` 将引擎纳入「是否已跑过」的判定；报告检测到混合引擎时会告警。旧的 HF 结果已移至 `evals/archive/`，不参与任何对比。

#### 可复现的程度（实测，不应过度推广）

**`enforce_eager` 是必需的，但它只解决一半问题。** 关闭 CUDA graphs 后，**小批量**下确实逐字相同（50 题 GSM8K 运行两遍：预测、文本、token 数全部相同，0 差异）——原因是 50 条序列可**全部同时在跑**，调度组成自始至终不变。

但**全量运行并非如此**。相同配置、相同代码、相同输入运行两轮全量（1319 / 200 / 164 题）：

| 评测项 | 逐题预测翻转 | 聚合分变化 |
| --- | --- | --- |
| 指令遵循（200） | 0 | 0 |
| HumanEval（164） | 0 | ±1~4 题（≤2.4pp） |
| MMLU chat（14042） | 0 ~ 150 | ≤±0.1pp |
| MMLU 纯文本（14042） | 125 ~ 211 | ≤±0.1pp |
| GSM8K（1319） | **74 ~ 197** | **≤±0.5pp** |

两条规律：

1. **输出越长，翻转越多。** 指令遵循与 HumanEval 的输出被停止符短促截断，翻转数为 0；GSM8K 需生成上千 token 的推理链，翻转率约 15%。这是自回归误差累积的直接体现。
2. **聚合分抖动均落在置信区间内**（MMLU ±0.8pp、GSM8K ±2.5pp），因此「模型之间比较优劣」不受影响，但**不应将 0.3pp 的差异视为结论**。

**根因**：GPU 上仅有约 41 路并发（`GPU KV cache size: 84,128 tokens / 2048`），1319 条题必须排队。每一步实际组成的批次取决于当时哪些序列尚未写完，调度组成的微小差异会使 GEMM 形状改变，bf16 下 argmax 偶尔翻转，并随后放大。

**该设计的代价需明确**：vLLM 换取的是 16.7× 速度与聚合稳定，而非逐题可复现。若要逐题复现，只能将并发压至极低（大批题目无法容纳），速度随之丧失，不划算。本文档上一版本曾记录「逐字相同」，该结论仅在 **50 题**上验证，却被直接推广至全量，属样本量不足导致的过度概括，已记入失败记录。

两个环境问题已在 `engines._prepare_env()` 中规避：调用方未激活环境时 `ninja` 不在 PATH（flashinfer 需现场编译）；本机 nvcc 为 CUDA 12.4，无法编译 flashinfer 0.6.18 所需的 `--compress-mode`，因此关闭 flashinfer 采样核。

## MMLU 有两个口径，不应混淆

| 口径 | 卷面 | 适用对象 |
| --- | --- | --- |
| `chat` | 带对话模板，`答案：` 位于 **user 回合内** | 经指令微调的模型 |
| `plain` | 纯文本 `Question: … Answer:`，无 chat 包装 | **基座** |

`chat` 口径下模型开始生成时已另起 `<|im_start|>assistant` 回合。instruct 模型知道「assistant 应作答」，**基座则不知道** —— 它将「答案：」与回合结束符理解为「这是一份已写完的文档」，随即**开启下一题**（复读题干）：

```
chat  口径  →  0/400  全部解析不出字母
plain 口径  →  281/400 = 70.2%
```

并且**不需要 few-shot**：`plain` 口径下 0/1/2/3/5-shot 完全相同（均为 17/20）。

**「base 0% → SFT 70.8%」这类写法是错误的**，它衡量的是格式适配，而非知识能力。

## 判分 bug 史（均不应改回）

### 1. JSONL 使用 `str.splitlines()` 切分

`splitlines()` 按 Unicode 定义的**所有**行边界切分，包括 `\x85`(NEL) / `\x0b` / `\u2028`，而 JSONL 的换行仅为 `\n`。MMLU 题库第 6956 行包含一个 `\x85`，该行被从 JSON 字符串中间切开，直接触发 `JSONDecodeError`，导致整个评测崩溃。

**应使用 `split("\n")`。** 更深一层的问题：本地校验脚本使用 `for line in f`，线上使用 `splitlines()`，两者切分方式不同，**本地校验通过而线上必然崩溃**。

### 2. 闭围栏正则锚定 `$`

原先剥离代码围栏使用 `re.sub(r"\s*```$", "", text)`，`$` 要求围栏位于字符串**最末尾**。而模型输出为：

    ```python
    def reverse_string(s):
        return s[::-1]
    ``` לחלוט

围栏后仍跟随乱码 token，`$` 无法匹配，围栏未被剥离，拼出的程序第一行为 ```` ``` ````，触发 SyntaxError。164 题中有 80 题失败，**真实 73.2% 被压低至 35.4%**，险些得出「SFT 使代码能力退化」这一完全相反的结论。

**闭围栏应自其出现位置起全部丢弃，不锚定末尾。**

### 3. 仅取「第一个 A-D」（MMLU）

原先 `LETTER_RE.search()` 取生成文本中**第一个** A/B/C/D。模型一旦复读题干，第一个字母即为选项标号 `A.` 而非答案，于是出现「生成字母 20/20 但正确率仅 10%」这类假分数。现按「整体即为字母 > 以字母开头 > 带标记 > 兜底」分级抽取，并统计各规则的命中数（兜底占比偏高说明该口径不可信）。

### 4. GSM8K 的 token 上限过小

`--gsm8k-max-new-tokens` 默认为 256 时，**冗长模型的答案会在最终给数之前被截断**，「抽取最后一个数字」将抽到中间值。同一样本 16 题：

| 模型 | 256 token | 1024 token | 被截断 |
| --- | --- | --- | --- |
| base-4b | 50.0% | 62.5% | 6/16 → 1/16 |
| sft-4b-v2 | 87.5% | 87.5% | 0/16 → 0/16 |
| instruct-2507 | **31.2%** | **87.5%** | **11/16** → 0/16 |

**风格差异被判定为能力差异。** 当前默认值为 1024，且诊断表会报告截断率。

---

### 5. `python_code` 仅判断「能否 parse」

Python 的标识符**允许中文**，因此「这不是代码」也能被 `ast.parse` 成功解析（解析为一个裸 `Name` 表达式），纯文本因此被判为合法代码。现要求 AST 中必须出现函数定义、调用、赋值等**代码结构**方可判定通过。

### 6. `follows_hash_format` 的判据过窄

原先要求「最后一行严格等于 `#### <数字>`」。实测两个模型均写作：

```
base          #### 数字
              18
sft           #### 数字: 18. (Janet makes $18 ...)
```

它们**将提示中的「数字」视为字面量**（提示词 `用「#### 数字」的格式` 确实存在歧义）。结果 sft 显示「按格式作答 0/400」，看似完全未遵从，实为判据错误。现改为「末尾 120 字内 `####` 后跟数字」，并要求其后存在数字（以排除基座 `#### 1. 计算…` 这类章节编号）。

提示词的歧义**已记录但未修改** —— 修改需重跑全部 GSM8K，而判分并不依赖格式（`last_number` 保证「只要写了数字即可判对」），列为已知待办。

### 7. `_lines()` 同样使用 `splitlines()`

与 JSONL 那次同源：`splitlines()` 按 Unicode 定义的**所有**行边界切分，`\x85` / `\u2028` / `\x0b` 均会被视为换行。影响 `single_line` / `line_count_eq` / `starts_with` / `line_prefix_count` / `line_starts_with_all` 五种规则。

实测 200 条指令遵循输出中 **0 条**包含此类字符，因此属**潜伏** bug（不同于 JSONL 那次会实际崩溃），但规则中的「只输出一行」「恰好 3 行」会因此误判。

### 8. `line_prefix_count` 使用了「至少」

题面均为「用**三个**要点…」，规则却写作 `n >= rule["n"]`，提供 5 个要点同样判定通过。该判据对冗长模型偏松（`sft-4b-v2` 正是较冗长的模型）。实测当前 0/7 触发，修改后分数不变，但口径正确。

### 9. 「口径无效」告警使用严格相等，样本量增大后失效

报告会在「某模型在某口径下抽不出答案」时标出「口径无效」，例如基座以 chat 口径做 MMLU 时，将提示视为已写完的文档继续生成，不输出任何选项字母。

判定原先写作 `unparsed == total`。**400 题时恰好成立**（干净的 400/400），切换至全量 **14042 题**后为 **14035/14042** —— 有 7 条碰巧输出了字母。严格相等随即落空，**告警从报告中消失**，而表上该单元格仍为醒目的 `0.0%`。这恰是最容易被误读为「模型不会做题」的单元格。

修改方式：阈值按**比例**判定（解析失败率 ≥ 99%，`UNUSABLE_UNPARSED_RATIO`），并在说明中给出真实比例，而非含糊的「全部」。

应记录的经验：**边界条件不应写作严格相等。** 「全部失败」「全部截断」这类判断在样本量增大后几乎必然出现零星例外，写成等值等于将告警绑定于特定样本量。报告中同样采用「比例告警」的截断率（`TRUNCATION_ALARM = 0.20`）一直工作正常。

### 10. 「截断档」告警读取的字段从未被写入

`make_report.py` 判断一份结果是否为 `--limit` 截断档时，读取 `requested["limit"]`。但 `eval.py` 写入 `requested` 时仅包含 `only` / `mmlu_style`（当时还带有一个 logits 口径开关，现已移除），**从未包含 `limit`**。该告警因此为死代码：一批仅跑了前 400 题的结果，在页面上与全量结果外观完全一致。

修改方式：`eval.py` 的 `requested` 增加 `limit`（未截断时写入 `None`）。

此类 bug 不会报错，也不会使任何数字变错，其效果是**让一项保护措施静默失效**。报告中的所有告警都应有一个「构造出触发条件」的验证，否则无法确认其是否仍在工作。

## 判分栈指纹：修改规则必须可被发现

结果 json 记录 `code.scoring_stack_sha`，即**整个判分栈**的聚合指纹：

```
eval.py（流程）  rules.py（24 种规则判定）  metrics.py（置信区间 + 退化指标）
answer_extract.py（数字/字母抽取）  code_extract.py（剥离围栏）
prompts.py（卷面原文）  engines.py（生成参数）  train_sft.py（停止符）
```

**必须覆盖全部文件**：判分逻辑拆分至多个文件后，若仅记录 `eval.py` 的 sha，会出现「修改了 `rules.py`（即修改了判分规则）而指纹不变」的情况 —— 两份结果会声称使用同一版代码，实际判定引擎不同。这正是指纹存在的唯一理由。

`prompts.py` 亦在内：它提供 GSM8K 与代码题的**卷面原文**，修改一个字的措辞分数即可能变化，属比判分更上游的变量。`engines.py` 同理：生成参数（采样、停止符截断语义）位于其中。

补跑脚本中另有一道护栏：开跑前记录一次 `scripts/*.py` 的 md5，跑完后再次比对，中途被修改则打印警告。**跑批期间不应修改 `scripts/` 下任何文件**；需要修改时应改完重跑，不应指望「跑完后再补一次重判」（这会使盘上代码与实际运行的代码不是同一版本）。

## 反面教材：两个「被修改坏」的尝试

上述各项均为真实 bug，以下两个为排查过程中的**误判**，记录于此以免重复：

**（1）认为 `$80,000` 会被拆碎。** 实测不会 —— `make_benchmarks.last_number` 的正则本就包含千分位。当时的「证据」来自临时编写的正则，而非线上代码。

**（2）认为应「优先取 `####` 之后的数字」。** 实测更差：**基座将 `####` 用作章节编号**（`#### 1. 计算每天的总产蛋量`），改为标记优先后基座由 55.8% 降至 45.2%。四种候选规则均已测试，现状（全文最后一个数字）最优，故**不作修改**。

应记录的经验：**修改判分逻辑前，应先在存档数据上测试全部候选规则。** 「看起来更严谨」的规则往往更差，而判分 bug 不会报错。
