# GRPO：负结果与不确定边界

阶段 3「GRPO + 可验证奖励」的一次完整尝试（IF-RLVR，AI2，arXiv 2507.02833）。

**结论**：主指标提升 **0.0pp（120/200 → 120/200）**。本轮究竟属于「失败」还是「评测方式不当」，现有数据无法判断 —— 缺少 IFBench。

数据来源为服务器实测（`outputs/grpo-4b-ifrlvr`）。评测产物未入库（`evals/results/*.json` 不进版本库），本文仅保留结论与归因。

环境为单卡 **RTX 5090 32G**（2026-10-06 换机后；上文主表那批结果出自 4090 24G）。训练运行于 `vllm` 环境（trl 1.14.1 + vllm 0.30 + transformers 5.18，colocate 模式）；原因（`tpt` 的 trl 0.24 与 transformers 5 不适配、server 模式需要 TRL 私有路由）见 `notes/workflow.md`。

## 一、主因：奖励形式无法作用于主指标的实际缺口（结构性，可确定）

该条最为确定，且在实验开始前即已注定。

主指标 8 类中，分值集中于两类：

| 类别 | 通过 | 说明 |
| --- | --- | --- |
| 数值约束 | **0/25** | 要求「输出即为一个纯数字」 |
| 长度约束 | **2/25** | 要求「恰好 N 字 / N 行」 |
| 其余 6 类 | 118/150 | 代码约束、禁忌词已接近满分（25/25、24/25） |

即：**200 题中 102 分来自已饱和的 6 类，50 题仅得 2 分。**

这 50 题的失败方式由 `flipped_by_junk_tail` 直接指出 —— `num-01~num-20`（20 条数值题**全部**在列）、`len-g03/g07/g09/…`、`lang-wc-1~5` 全部在列。它们在输出正确答案后，收尾额外生成一个乱码 token（`72` → `72 לחלוט`），导致「纯数字」约束不通过。

GRPO 的奖励为**「通过约束的比例」**，是**整条序列的函数**；而乱码尾的靶心是 `<|im_end|>` 那**一个 token** 的 logit（项目已量化：排名第 4，仅相差 0.13 nats）。序列级信号无法作用于单个 token，因此 **GRPO 在结构上无法修复该缺口**。

该结论并非首次得出，而是项目第 **14** 次验证同一现象（SFT 侧 6 + DPO 5 + RFT 2 + GRPO 1）。更换奖励形式亦不影响该结论。

**旁证**：`junk_tail` 由 178 升至 **184（增加 6）**。GRPO 未改善收尾，反而略微加重。

## 二、次因：更新幅度过小，模型基本未变化（可确定，非主因）

| 证据 | 值 | 含义 |
| --- | --- | --- |
| `kl` | 均值 0.0009、max 0.0032 | 策略几乎未偏离起点 |
| 主指标 | 120 → 120 题 | 无一道跨过门槛 |
| `junk_tail` / `trimmed` | 178→184 / 154→150 | 均在噪声范围内 |
| 分类别 | +1（格式）−1（语言） | 相互抵消 |

`lr = 1e-6` 取自论文（论文的全参 8B 使用 5e-7），但**本脚本使用的是 LoRA** —— LoRA 的常用 lr 比全参高 10~100 倍。因此「模型未发生变化」有参数依据。

需要说明的是，**即使调大 lr，主指标大概率仍不会提升**，因为瓶颈位于第一节（乱码尾）；lr 只是使本轮「未变化」的程度更为明显。

## 三、另有两项次要因素（可确定，量级较小）

1. **约 1/3 的样本不产生梯度**：`frac_reward_zero_std` 全程稳定在 **0.32~0.34**，即 1/3 的 prompt 组内 8 条全对或全错，优势为 0，这些数据不产生梯度贡献。
2. **数据量与可提升空间**：1500 条 prompt（论文使用 60k~100k）；且起点在这些英文约束上已有 0.23 的通过率，可提升空间本身有限。

## 四、最大的不确定性：评测口径可能不适用（未测，无法判定）

该条必须列出，因为它决定了上述全部结论的**适用范围**。

| | 训练侧 | 评测侧 |
| --- | --- | --- |
| 语言 | 英文约束描述（IFEval 25 + IFTrain 29） | **中文**模板题 |
| 约束类型 | 54 种，其中 29 种为 IFBench 全新设计 | 自建的 8 类 24 种规则 |
| 用途 | 训练 | 同时也是项目历史基线 |

IF-RLVR 论文的目标是**「精确指令遵循的泛化」**，其标准度量为 **IFBench（58 个全新约束、299 条 held-out、来源 WildChat）**，而 IFBench **尚未运行任何一条**。

论文另有一项直接相关的发现：**模型会过拟合到 IFEval 的 25 个模板**（2B 模型即可在 IFEval 上取得 80+）。本项目的训练数据恰好包含这 25 个模板。因此训练集 reward 升至 0.319，**有可能来自模板记忆**，而该问题仅 IFBench 能够识别。

当前状态如下：

| 问题 | 是否可回答 |
| --- | --- |
| 主指标是否提升 | 可回答：未提升（0.0pp） |
| 乱码尾是否改善 | 可回答：未改善（184，增加 6） |
| 其他能力是否退化 | 可回答：未退化（MMLU / GSM8K / HumanEval 均在抖动范围内） |
| **本轮 GRPO 是否学到内容** | **无法回答 —— 缺少 IFBench** |
| lr 过小是否为主因 | 只能确认更新幅度确实很小，但不能据此判定其导致主指标未提升 |

## 结论归纳

**未能提升的直接原因是奖励形式无法作用于瓶颈** —— 主指标 50 分的缺口集中在收尾的单个 token 上，而序列级奖励天然无法作用于该位置；这也解释了训练集 reward 提升 39% 而评测结果未变的现象。但「本轮方法本身无效」这一更强的结论，现有数据并不支持，因为评测使用的是被乱码尾污染、且与训练分布不同源的中文口径。

## 后续工作

**补充 IFBench。** 它是判定方法是否有效的唯一口径，也是该方向从「负结果」走向「结论」的必经步骤。判分器已 vendor 至 `scripts/ifbench/`（上游原样副本，含 299 条 held-out 的 `IFBench_test.jsonl`），仅需将其接入既有评测栈（`scripts/eval_pipeline.py`）。
